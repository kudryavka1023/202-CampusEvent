# CampusEvent 设计原则与模式决策报告

> 配套文档：`设计说明书.md`、`06-design-class.drawio`、`06-design-class-architecture.drawio`、三张顺序图、`../requirements/SRS.md`。
> 版本：v1.0（2026-11-22）。本报告只讨论“为什么这样设计”，不复述全部字段；字段与接口契约以设计说明书为准。

## 1. 报告要回答的问题

实验二要求“先做设计决策，再指导 AI 实现”，并且明确反对“用了设计模式所以扩展性好”这种空话。本报告用四个问题约束每个决策：

1. **问题**：不改设计会出什么具体问题？给出触发场景。
2. **备选**：至少两个可选方案，包括“最笨但可行”的方案。
3. **选择与理由**：为什么选它；用哪个类、哪条消息、哪张图证明。
4. **成本与验证**：多了哪些类/间接层；未来哪种变更会受益；用什么指标验证。

涉及的初始需求：P2-F01～P2-F08；验收：C1～C10；规则：附录 B.1～B.3。

## 2. 设计原则总览

| 原则 | 本设计的落点 | 具体证据 |
|---|---|---|
| 单一职责 SRP | 实体只做自身状态；服务只做用例协调；策略只决定初始状态；观察者只写通知；仓储只做持久化 | `Activity.isOpen/hasCapacity`；`Registration.approve/reject/cancel`；`DirectRegistrationPolicy` 只返回 `APPROVED` |
| 开闭原则 OCP | 新增报名方式不改 `RegistrationService.submit`；新增通知渠道不改发布者 | 策略接口 + 工厂；观察者接口 + 订阅 |
| 里氏替换 LSP | 两个策略实现同一契约，返回合法初始状态，不加强前置条件 | `decideInitialStatus` 契约测试 |
| 接口隔离 ISP | 策略、观察者、四个聚合仓储都是小接口 | 调用方不依赖无关方法 |
| 依赖倒置 DIP | 服务依赖 `ActivityRepository`/`RegistrationRepository`/`RegistrationEventPublisher`/`TransactionManager` 接口 | 架构类图虚线依赖；SQLite 实现在基础设施层 |
| GRASP 信息专家 | 容量/时间判断放 `Activity`；状态迁移放 `Registration` | 实体方法而非“贫血 + 服务全包” |
| GRASP 创建者 | `RegistrationService` 创建 `Registration`；观察者创建 `Message` | 创建者拥有初始化所需数据与事务 |
| GRASP 控制器 | 5 个控制器按用例分组 | `ActivityController`、`RegistrationController` 等 |
| GRASP 低耦合/高内聚 | 通知与报名解耦；策略只承担一个变化点 | 事件发布者、策略接口 |
| GRASP 保护变化 | 策略保护“报名方式”变化；观察者保护“通知渠道”变化；仓储保护“存储”变化 | 三个稳定接口 |

## 3. SOLID 逐项论证

### 3.1 SRP：为什么把“报名”拆成实体、服务、策略、观察者

**问题：** 如果把“校验名额、决定状态、写通知、存数据库”都放进 `Registration` 实体，实体会同时因业务规则、通知渠道、数据库 schema 三种原因变化；任何一处改动都可能影响另外两处。

**备选：**

- A. 富实体：`Registration.submit()` 内部查仓储、发通知。
- B. 贫血实体 + 事务脚本：所有逻辑在 `RegistrationService`。
- C. 实体 + 服务 + 策略 + 观察者 + 仓储（本设计）。

**选择与理由：**

- `Registration` 只负责“我的状态是否允许迁移”，例如 `approve()` 只在 `PENDING` 时成功；它不查数据库、不发通知。
- `RegistrationService` 负责用例级协调：加载、校验公共规则、开启事务、调用策略、保存、发布事件。
- `RegistrationPolicy` 只回答“初始状态是 `APPROVED` 还是 `PENDING`”。
- `MessageNotificationObserver` 只负责把事件变成站内消息。

这样，通知渠道变化不会碰实体；数据库变化不会碰策略；报名方式变化不会碰观察者。

**成本：** 类比“事务脚本”多出 5 个协作类；阅读一个报名流程需要跨 3 张图。**缓解：** 顺序图把消息按调用顺序编号，设计说明书 4.2.2 给出“消息 → 方法”对照表。

**反例（明确不采用）：** 在 `Registration` 里注入 `MessageRepository`。这会让实体依赖基础设施，单元测试必须搭数据库，且通知失败会污染实体状态。

### 3.2 OCP：新增“抽签/候补”时不改主流程

**问题：** 初始版本只有 `DIRECT` 与 `APPROVAL`。教师变更单很可能新增“抽签”或“候补”。如果 `submit` 里写：

```python
if activity.policyType == "DIRECT":
    status = APPROVED
elif activity.policyType == "APPROVAL":
    status = PENDING
elif activity.policyType == "LOTTERY":
    ...
```

每加一种方式都要改 `RegistrationService.submit`，并回归所有报名用例；分支还会与公共规则（名额、重复）纠缠。

**备选：**

- A. 上述 `if/elif`。
- B. 继承 `RegistrationService`，为每种方式建子类。
- C. 策略接口 + 具体策略 + 工厂（本设计）。

**选择与理由：**

- 选 C。`submit` 只调用 `policyFactory.create(activity.policyType)` 与 `policy.decideInitialStatus(context)`；新增方式 = 新增一个实现 + 注册到工厂 + 枚举/数据库 CHECK 增一个值。主流程零修改。
- B 的问题：继承会把事务、校验、事件发布复制到子类，或者让子类依赖父类的受保护方法；组合优于继承。
- A 的问题：违反 OCP，且 `submit` 会随方式数量增长。

**证据：** `06-design-class.drawio` 中 `RegistrationService --> RegistrationPolicy` 是依赖抽象；`DirectRegistrationPolicy`/`ApprovalRegistrationPolicy` 实现同一接口；`07-提交报名-sequence.drawio` 的策略分支只有两条消息。

**成本：** 多 3 个类（接口 + 2 实现）和 1 个工厂；调试时要确认工厂返回了哪个实现。**缓解：** 工厂启动时注册全部策略，缺失时 `POLICY_NOT_CONFIGURED` 快速失败；策略单测覆盖返回值。

### 3.3 LSP：策略契约必须可替换

**契约（写在接口注释与测试里）：**

- 前置：`context.activity` 非空，`context.now` 非空，`approvedCount >= 0`。
- 后置：返回 `RegistrationStatus.APPROVED` 或 `RegistrationStatus.PENDING`；不修改 `context`；不写数据库；不抛业务异常（配置缺失除外）。
- 不变量：返回 `APPROVED` 时调用方仍会检查容量；返回 `PENDING` 时调用方不占名额。

**为什么这很重要：** 如果某个策略返回 `REJECTED`，`submit` 的“成功时恰有一条有效报名”后置条件就被破坏；如果策略自行检查名额并返回 `PENDING`，公共规则会出现两套实现，且策略需要访问仓储，违反依赖方向。

**验证：** 对每个实现跑同一组契约测试：返回值为合法枚举、上下文未被修改、不调用仓储（用 mock 断言零交互）。

**成本：** 契约比“能跑就行”更严格，新增策略必须遵守；但这是可替换性的前提。

### 3.4 ISP：为什么仓储按聚合拆成四个接口

**问题：** 如果做一个“大而全”的 `Repository`，报名服务会依赖活动、消息、学生的方法；单元测试要 mock 大量无关方法，接口变化会影响所有调用方。

**选择：** `ActivityRepository`、`RegistrationRepository`、`MessageRepository`、`StudentRepository` 四个小接口，按聚合边界拆分。`RegistrationService` 只依赖它真正使用的两个仓储 + 策略工厂 + 事件发布者 + 事务管理器。

**成本：** 接口数量增加；跨聚合查询（如审批/我的报名列表带学生姓名、活动名称）需要 JOIN 或由服务组合。**缓解：** 这些查询放在 `RegistrationRepository`，返回读模型；不为读模型再拆一个接口（避免过度设计）。

### 3.5 DIP：服务不知道 SQLite 的存在

**问题：** 如果服务直接 `sqlite3.connect`，单元测试必须用真实数据库，换 PostgreSQL 要改业务代码，SQL 错误会穿透到用例层。

**选择：** 服务依赖接口；`SqliteActivityRepository` 等实现放在基础设施层，在组合根注入。事务管理器也以接口/上下文形式注入，服务不直接拼 `BEGIN`。

**证据：** `06-design-class-architecture.drawio` 中服务 → 仓储是虚线依赖；SQLite 实现类不在领域图中。

**成本：** 需要写映射代码（行 → 对象），事务边界要显式管理；比 Active Record 多一层。**收益：** 服务测试可用内存实现或临时 SQLite；换库只改基础设施层。

## 4. GRASP 逐项论证

| GRASP 模式 | 本设计的选择 | 理由 | 代价 |
|---|---|---|---|
| 信息专家 | `Activity.isOpen/hasCapacity/remainingSeats`；`Registration.isActive/isOwnedBy/approve/reject/cancel` | 这些行为只依赖对象自己的字段，放在实体里内聚最高 | 实体方法变多；但比“服务直接改字段”更安全 |
| 创建者 | `RegistrationService` 创建 `Registration`；`MessageNotificationObserver` 创建 `Message` | 创建者拥有初始化所需数据（学生、活动、状态、时间）与事务边界 | 服务职责增加；用工厂方法/构造器约束必填字段 |
| 控制器 | 控制器按用例分组；多数只依赖一个服务 | 界面适配与业务协调分离；活动详情页只读组合活动/报名/统计三个服务 | 控制器数量增加；路由映射要维护 |
| 低耦合 | 服务不直接依赖 `MessageRepository`；通过发布者/观察者 | 通知渠道变化不影响报名主流程 | 多一层间接；同步调用有延迟 |
| 高内聚 | 策略只决定初始状态；观察者只写消息 | 一个类只有一个变化原因 | 需要清晰命名，避免“策略类什么都管” |
| 多态 | `RegistrationPolicy` 两个实现 | 消除 `if policyType` | 需要工厂与注册表 |
| 间接 | `RegistrationEventPublisher`、Repository | 隔离通知渠道与存储 | 调试链路变长 |
| 保护变化 | 策略/观察者/仓储 | 三个最可能变化的方向被隔离 | 抽象成本 |

**特别说明“信息专家”与“服务协调”的边界：** 名额判断需要“已通过数”，这个计数不在 `Activity` 对象里（避免实体持有全量报名）。因此 `Activity.hasCapacity(approvedCount)` 只做纯判断，计数由 `RegistrationRepository` 提供，服务负责把两者接起来。这是“信息专家 + 服务协调”的组合，不是把规则漏到服务。

## 5. 模式决策一：Strategy（报名策略）

### 5.1 问题场景

- C2：直接报名 → 立即 `APPROVED`。
- C5：审核型 → `PENDING`。
- 未来 CR：抽签/候补 → 可能是 `PENDING` + 候补位，或直接 `APPROVED`。

如果主流程用 `if/elif`，每加一种方式都要改 `submit`，并且容易把“名额检查”写进某个分支，造成两套规则。

### 5.2 备选与评分

| 方案 | 新增方式改动点 | 公共规则复用 | 可测试性 | 结论 |
|---|---|---|---|---|
| 主流程 `if/elif` | 修改 `RegistrationService.submit` | 容易复制/分叉 | 需集成测试 | 否决 |
| 继承 `RegistrationService` | 新增子类，复制事务/校验 | 父类方法受保护，易耦合 | 需构造父类依赖 | 否决 |
| 策略 + 工厂 | 新增策略类 + 注册 | 公共规则留在服务，天然复用 | 策略可单测 | **选择** |

### 5.3 参与类与协作

- `RegistrationPolicy`（接口）：`policyType()`、`decideInitialStatus(context)`。
- `DirectRegistrationPolicy`：返回 `APPROVED`。
- `ApprovalRegistrationPolicy`：返回 `PENDING`。
- `RegistrationPolicyFactory`：`Map<PolicyType, RegistrationPolicy>`，`create(type)` 查找；缺失抛 `POLICY_NOT_CONFIGURED`。
- `RegistrationService`：构造 `RegistrationContext`，调用工厂与策略，拿到状态后创建记录。

### 5.4 成本

- +1 接口、+2 实现、+1 工厂；启动时注册表初始化。
- 多一层间接：读代码要从服务跳到策略；用顺序图与“消息 → 方法”表缓解。
- 如果未来只有两种方式且永不扩展，策略是过度设计；但实验二明确要求“面对教师变更请求”，且变更方向可预期，因此值得。

### 5.5 验证指标（变更阶段实测）

- 新增抽签：新增类数 1～2；修改核心业务类数 0（枚举/DB CHECK 除外）；C1～C10 回归失败 0。
- 对照 `if/elif` 基线：预计修改 `RegistrationService` 1 个核心类、增加 1 个分支、回归报名相关用例 6～8 条。实际数据在变更版报告中记录。

## 6. 模式决策二：Observer（通知解耦）

### 6.1 问题场景

- 报名/审批/取消后要写站内消息（P2-F07）。
- 通知可能失败；失败不能让已提交的报名消失（附录 B.2-6）。
- 未来可能加邮件/短信/审计，但初始版本不做。

### 6.2 备选

| 方案 | 耦合 | 失败影响 | 扩展性 | 结论 |
|---|---|---|---|---|
| 服务直接写 `MessageRepository` | 高：报名依赖消息表 | 通知异常可能回滚报名 | 加渠道要改三个方法 | 否决 |
| 观察者/事件分发（本设计） | 低：服务只依赖发布者接口 | 发布者捕获异常，报名不受影响 | 加观察者即可 | **选择** |
| 消息队列 | 最低 | 需重试/死信/最终一致 | 最好 | 初始版本过度 |

### 6.3 时序与事务语义

1. `RegistrationService` 在写事务内完成“校验 + 状态迁移 + 保存”。
2. `COMMIT` 之后构造 `RegistrationEvent` 并 `publish`。
3. `SimpleRegistrationEventPublisher` 遍历观察者，每个观察者独立 `try/except`。
4. `MessageNotificationObserver`：
   - `existsByEventKey(eventKey)`；已存在则跳过；
   - 否则 `save(Message)`；唯一约束冲突也视为已通知。
5. 观察者异常 → `NotificationFailureLogger.log(event, error)`；不向服务抛出。

**为什么在事务外发布：** 如果在事务内发布，观察者写消息会加入同一事务；通知失败会回滚报名，违反“报名优先”。事务外发布让报名先落库，通知成为可补偿的副作用。

**残留风险：** `COMMIT` 与 `publish` 之间进程崩溃，通知会丢失且没有失败日志。初始版本用启动补偿脚本（扫描无消息的有效报名并补发）兜底；变更版可改为事务性 Outbox：在同一事务写 `outbox` 行，后台调度器发送并标记。**这是有意识的取舍，不是忽略。**

### 6.4 幂等

- `eventKey = registrationId + ":" + eventType`；`messages.event_key` 唯一。
- 先查后插有竞态；唯一约束是最终防线；捕获冲突按“已通知”处理。
- 为什么不用自增消息 ID 做幂等：事件重放时 ID 会变；业务键更稳定。

### 6.5 成本

- 同步发布增加一次消息插入的延迟（约 1 次 SQLite 写）；可接受。
- 需要处理幂等、失败日志、事件顺序；比直接调用多代码。
- 观察者是进程内的，不是“事件驱动架构”；不宣称最终一致性或高可用。

## 7. 模式决策三：Factory（策略工厂）

**问题：** 谁来决定用哪个策略？如果服务里 `if type == DIRECT: new Direct...`，等于把 OCP 问题从状态判断挪到了对象创建。

**备选：**

- A. 服务内 `if/elif` 创建。
- B. 工厂方法（每个类型一个静态方法）。
- C. 注册表工厂（本设计）：`register(policy)` + `create(type)`。

**选择 C 的理由：**

- 新增策略只需在组合根注册，服务与工厂都不改。
- 启动时能检查“枚举值是否都有策略”，缺失快速失败。
- 比 B 少一个“每加类型改工厂”的改动点。

**成本：** 注册表初始化顺序；如果忘记注册，运行时才报错。**缓解：** 组合根集中注册 + 启动自检（遍历 `PolicyType` 调 `create`）。

## 8. 模式决策四：Repository（持久化边界）

**问题：** 领域对象是否直接执行 SQL？服务是否直接依赖 SQLite？

**备选：**

- A. Active Record：实体自带 `save/find`。
- B. 事务脚本 + 裸 SQL 在服务里。
- C. Repository 接口 + 基础设施实现（本设计）。

**选择 C 的理由：**

- 实体可脱离数据库单测；状态迁移测试不需要建表。
- 换存储（PostgreSQL/内存）只改实现；服务不动。
- SQL 集中在基础设施层，便于审查索引与事务。

**成本：**

- 行 → 对象的映射代码；查询方法按用例定制（如 `findActive`），有“仓储变查询对象”的风险。
- 事务边界要显式管理；服务必须知道何时 `BEGIN IMMEDIATE`。

**边界控制：** 仓储只做“按聚合存取 + 必要的计数/存在性查询”，不写业务规则；跨聚合的协调在服务。`countByActivityAndStatus` 是名额规则所需的计数，属于仓储的查询职责，不是规则本身。

## 9. 模式决策五：值对象与结果对象

| 值对象 | 解决的问题 | 不用的后果 |
|---|---|---|
| `RegistrationContext` | 策略需要学生、活动、时间、已通过数；一次性传入，避免策略查库 | 策略依赖仓储，违反 DIP；参数列表过长 |
| `RegistrationResult` | 预期失败（重复/满员/状态冲突）不用异常穿过层边界 | 控制器要捕获多种异常；事务回滚与业务失败混淆 |
| `ActivityResult` | 活动 CRUD 的成功/失败统一 | 控制器分别处理 `Optional`/布尔/异常 |
| `ActivitySummary` | 列表需要活动字段 + 聚合计数 + 展示状态 | 实体承担查询职责；模板里 N+1 查询 |
| `ActivityStatistics` | 统计页三数一致 | 控制器拼三个查询，快照不一致 |
| `RegistrationSummary` | 报名列表需要学生姓名/活动名称 + 提交时间，且避免 N+1 | 控制器逐条查学生/活动；或把 `StudentRepository` 注入审批服务 |
| `RegistrationEvent` | 通知所需的最小事实 + 幂等键 | 观察者反查数据库，耦合加深 |

**成本：** 多几个类与映射；但比“传 Map/元组”更可读、可测试。

## 10. 公共规则与策略责任的划分（设计任务 B）

### 10.1 结论

| 规则 | 责任方 | 理由 |
|---|---|---|
| 活动存在、未开始 | `Activity.isOpen` + `RegistrationService` | 与报名方式无关；实体最了解自己的时间 |
| 无重复有效报名 | `RegistrationService` + 部分唯一索引 | 跨记录查询；数据库兜底并发 |
| 名额未满 | `RegistrationService` + `Activity.hasCapacity` | 需要聚合计数；两种方式共用 |
| 角色/归属 | 控制器 + 服务 | 与报名方式无关 |
| 初始状态 | `RegistrationPolicy` | 唯一随方式变化的点 |
| 是否需要审批 | 由 `PENDING` 状态隐含 | 不额外加布尔字段，避免不一致 |

### 10.2 如果把名额检查放进策略会怎样

- 直接策略与审核策略都要写“count + capacity”，两套实现容易分叉（一个用 `>=`，一个用 `>`）。
- 策略需要访问 `RegistrationRepository`，从“纯决策”变成“查库 + 决策”，无法脱离数据库单测。
- 批准时的名额复查仍然必须在服务/审批流程做，策略管不到；规则被拆成两处。
- 新增抽签策略时，作者可能忘记检查名额，导致超卖。

因此，策略只做“状态决策”，公共规则集中在服务与实体。这是本设计最重要的职责边界。

## 11. 通知失败与幂等（设计任务 C）

### 11.1 失败是否影响报名事务

**不影响。** 顺序：报名事务提交 → 发布事件 → 观察者写消息。通知失败只写日志，不回滚报名。理由：

- 报名是用户的核心目标；通知是辅助结果。
- 如果通知失败回滚报名，用户会看到“报名失败”，但实际上名额可能已被占用/释放，语义混乱。
- 日志提供可追踪性，补偿脚本可以重放。

### 11.2 如何避免重复通知

- `eventKey = registrationId:eventType`，数据库唯一。
- 观察者先查后插；并发冲突按已通知处理。
- 事件重放（补偿脚本）使用同一 `eventKey`，不会重复。

### 11.3 与消息队列方案的区别

| 维度 | 本设计（进程内观察者） | 消息队列 |
|---|---|---|
| 部署 | 单进程，无额外组件 | 需 broker、序列化、重试、死信 |
| 一致性 | 提交后同步发布；崩溃窗口存在 | 可做 Outbox/事务消息，最终一致 |
| 失败处理 | 日志 + 补偿脚本 | 自动重试 + 死信队列 |
| 适用 | 课程规模、单机 | 高吞吐、多消费者、跨服务 |

结论：初始版本选观察者；接口保留，未来可替换为 MQ 发布者，服务层不变。

## 12. 架构原则：分层与依赖方向

### 12.1 为什么是分层单体，不是微服务

- 初始版本 8 个主用例 + 1 个扩展用例（UC3a）、4 张表、单机部署；微服务的网络调用、分布式事务、服务发现成本远大于收益。
- 分层单体仍能通过接口隔离变化；未来若拆服务，Repository/Publisher 接口是天然边界。
- 课程周期有限，部署与调试成本必须可控。

### 12.2 依赖规则的反例

| 反例 | 后果 |
|---|---|
| 控制器直接 `sqlite3` 查询 | 业务规则散落，无法单测，SQL 注入风险 |
| 实体导入 Flask `request` | 领域层依赖 Web 框架，无法复用 |
| 服务 `new SqliteRegistrationRepository()` | 无法替换/ mock，违反 DIP |
| 观察者直接改 `Registration.status` | 绕过服务事务与状态机，数据不一致 |

### 12.3 组合根

应用启动时集中装配：

```text
connection = open_sqlite(...)
tx = SqliteTransactionManager(connection)
activityRepo = SqliteActivityRepository(connection)
registrationRepo = SqliteRegistrationRepository(connection)
messageRepo = SqliteMessageRepository(connection)
studentRepo = SqliteStudentRepository(connection)  # 仅演示登录适配器使用
policyFactory = RegistrationPolicyFactory([Direct..., Approval...])
publisher = SimpleRegistrationEventPublisher([MessageNotificationObserver(messageRepo)], logger)
activityService = ActivityService(activityRepo, registrationRepo, tx)
registrationService = RegistrationService(activityRepo, registrationRepo, policyFactory, publisher, tx)
```

只有组合根知道具体实现；控制器通过依赖注入拿到服务。测试时替换为内存实现/假发布者。

## 13. 成本汇总与“不做什么”

| 决策 | 增加的成本 | 不做的后果 | 是否值得 |
|---|---|---|---|
| 策略 + 工厂 | 4 个类、注册表、间接层 | 每加方式改主流程，规则分叉 | 值得（变更可预期） |
| 观察者 | 发布者、观察者、幂等、日志 | 通知耦合报名，失败回滚风险 | 值得（明确要求解耦） |
| Repository | 4 个接口 + 映射 + 事务 | 领域依赖 SQL，难测试/换库 | 值得（可测试性） |
| 值对象 | 7 个类、映射 | 参数膨胀、异常穿透、N+1 | 值得（边界清晰） |
| 分层 | 更多文件与包 | 控制器/实体耦合 | 值得（课程要求与维护） |

**明确不做：**

- 通用事件总线、CQRS、事件溯源：当前只有一种领域事件，过度设计。
- 泛型 Repository / 抽象 BaseService：查询差异大，抽象会泄漏。
- 软删除：所有查询都要过滤，容易漏；选择拒绝删除并提示。
- 乐观锁/版本号：SQLite 单写者 + `BEGIN IMMEDIATE` 已足够；多实例时再引入。
- 分布式事务/Outbox：初始版本用日志 + 补偿脚本；变更版再评估。

## 16. 一页结论

- **职责**：实体管自身状态，服务管用例与事务，策略管初始状态，观察者管通知，仓储管持久化。
- **变化点**：报名方式用 Strategy + Factory 隔离；通知渠道用 Observer 隔离；存储用 Repository 隔离。
- **规则**：名额、重复、活动状态是公共规则，集中在服务/实体；策略不重复实现。
- **一致性**：报名先提交，事件后发布；通知失败写日志不回滚；`eventKey` 幂等。
- **并发**：`BEGIN IMMEDIATE` 串行化写 + 部分唯一索引兜底；批准时复查名额。
- **取舍**：接受同步通知的延迟与崩溃窗口，换取单机部署与简单事务；未来用 Outbox/MQ 替换发布者，不改服务。
- **验证**：用 C1～C10、E1～E10 与变更指标证明设计，而不是用“模式数量”证明。
