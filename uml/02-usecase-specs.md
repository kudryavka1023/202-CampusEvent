> 配套 SRS：`../requirements/SRS.md`（评审稿）

---

## 1. 文档目的与范围

本文档把实验二的初始业务需求整理为可评审、可实现、可测试的用例模型，作为后续分析类图、设计类图、时序图与设计说明书的输入。

**本文档回答的问题：**

1. 系统有哪些参与者，各自能启动哪些用例。
2. 每个用例的触发器、前置/后置条件、基本流与扩展流是什么。
3. 哪些规则是公共业务规则，哪些是报名方式带来的差异。
4. 每条功能需求如何追溯到用例与验收用例。

**本文档不回答的问题：**

- 采用什么框架、数据库表如何建、类如何拆分（属于设计阶段）。
- 教师变更单的具体内容与实现（变更单发布后再做影响分析）。
- 用户注册、登录、复杂权限（初始版本使用固定演示账号，见假设 A-1）。

## 2. 术语与缩写

| 术语 | 定义 |
|---|---|
| 活动（Activity） | 校园管理员发布的一次可报名事件，含名称、类型、开始时间、地点、容量、报名方式。 |
| 报名（Registration） | 一名学生对一个活动提交的一条报名记录，具有状态与时间戳。 |
| 有效报名 | 状态为“待审核（PENDING）”或“已通过（APPROVED）”的报名；同一学生同一活动最多一条。 |
| 历史报名 | 状态为“已拒绝（REJECTED）”或“已取消（CANCELLED）”的报名；保留记录，允许再次申请。 |
| 直接报名（DIRECT） | 报名方式之一：公共规则通过后，报名立即变为“已通过”。 |
| 审核型报名（APPROVAL） | 报名方式之一：提交后为“待审核”，由管理员批准或拒绝。 |
| 名额 | 活动容量 `capacity`；只由“已通过”报名占用，待审核不占名额。 |
| 站内通知 | 写入 `Message` 的消息，学生在通知页面查看；不接邮件/短信。 |
| 公共规则 | 与报名方式无关的规则：活动可报名、无重复有效报名、名额未满、角色/归属正确。 |
| 策略（Policy） | 设计阶段对“报名方式差异”的抽象；需求阶段只描述两条备选流，不引入实现词。 |

## 3. 参与者

| 参与者 | 类型 | 说明 | 主要目标 |
|---|---|---|---|
| 学生（Student） | 主要业务参与者 | 使用固定演示账号进入系统；只能查看/操作自己的报名与通知。 | 浏览活动、报名、取消报名、查看通知。 |
| 管理员（Admin） | 主要业务参与者 | 使用固定演示账号进入系统；负责活动发布、审批与统计。 | 管理活动、审批报名、查看统计。 |

**不设立的参与者：**

- “定时器/时间”不作为参与者。活动是否开始由系统在报名时读取当前时间判断，不涉及后台定时任务。
- “通知渠道”不作为参与者。站内消息是系统内部职责，不接外部服务。
- “数据库”不是参与者，属于设计阶段的持久化机制。

## 5. 用例图说明

用例图见 `01-usecase.drawio`。图中只画参与者、用例、关联与一条 `«extend»`，不画实现类、数据库或框架。

### 5.1 为什么把“查看活动详情”建成 `«extend»`

- 基用例 UC3“浏览/筛选活动”在只显示列表时仍然是一个完整、可结束的用例。
- 查看详情只在学生选择某一个活动时发生，可能发生 0 次。
- 因此 UC3a → UC3 用 `«extend»`，扩展点为“学生选择某一活动”，而不是 `«include»`。

### 5.2 为什么“直接报名/审核型报名”不拆成两个用例

- 两个路径的触发器相同（学生点击“报名”），目标相同（完成一次报名申请），只是结果状态不同。
- 若拆成两个用例，会把“报名方式”这一变化点固化在需求模型里，后续新增“抽签/候补”还要再加用例。
- 本规格把两条路径写成 UC4 的**备选流**（A-1/A-2 之外的分支），设计阶段再用策略模式承载差异。这样需求模型稳定，变化点留到设计阶段处理。

### 5.3 为什么没有其他 `«include»`

- “校验活动是否开始”“校验重复报名”“校验名额”都是 UC4 内部的公共规则，不是参与者可独立启动、有独立可观测结果的用例，不能为了画 `«include»` 而把它们升格为用例。
- “写站内通知”是 UC4/UC5/UC6 的系统职责与后置条件，不是学生主动启动的用例；学生查看通知由 UC8 单独表达。

## 6. 用例规格

### UC1 创建活动

- **用例编号**：UC1
- **用例名称**：创建活动
- **参与者**：管理员（主要）
- **描述**：管理员填写活动名称、类型、开始时间、地点、人数上限与报名方式，创建一个可供学生浏览和报名的活动。
- **触发器**：管理员在活动管理页点击“创建活动”。
- **前置条件**：
  1. 管理员已进入管理端（固定演示账号）。
- **后置条件**：
  1. 成功时存在一条新的活动记录，字段完整，`capacity > 0`，`start_at` 晚于当前时间。
  2. 新活动没有报名记录。
  3. 活动出现在学生端活动列表中。
- **基本事件流**：
  1. 管理员打开创建活动表单。
  2. 系统显示表单：名称、类型、开始时间、地点、人数上限、报名方式（默认“直接报名”）。
  3. 管理员填写并提交。
  4. 系统校验必填项、名称长度、容量为正整数、开始时间晚于当前时间、报名方式为 `DIRECT` 或 `APPROVAL`。
  5. 系统生成活动 ID 与创建/更新时间，保存活动。
  6. 系统提示“创建成功”，返回活动管理列表。
- **扩展事件流**：
  - **A-1 必填项缺失或格式错误**：系统在对应字段旁提示错误，保留已填内容，不保存，返回基本流第 3 步。
  - **A-2 人数上限 ≤ 0 或非整数**：提示“人数上限必须为正整数”，不保存。
  - **A-3 开始时间不晚于当前时间**：提示“开始时间必须晚于当前时间”，不保存。
  - **A-4 报名方式非法**：提示“报名方式配置错误”，不保存。
  - **A-5 持久化失败**：事务回滚，提示“创建失败，请重试”，不产生半条记录。
- **补充约束**：
  - D-1 活动字段见第 8 节 D-2。
  - B-1 容量为正整数；活动开始前允许报名。
  - B-2 报名方式只有直接报名、审核型报名两种。
  - N-1 创建操作响应时间 ≤ 2 秒（正常数据规模）。
- **未包含**：草稿、定时发布、活动图片、活动取消/归档（见第 12 节）。

### UC2 编辑/删除活动

- **用例编号**：UC2
- **用例名称**：编辑/删除活动
- **参与者**：管理员（主要）
- **描述**：管理员修改已有活动的字段，或删除一个尚未产生报名记录的活动。
- **触发器**：管理员在活动管理列表选择活动，点击“编辑”或“删除”。
- **前置条件**：
  1. 管理员已进入管理端。
  2. 目标活动存在。
- **后置条件**：
  1. 编辑成功时活动字段更新，且不违反容量/报名方式/时间约束。
  2. 删除成功时活动及其无关联的数据被删除；不存在孤立报名记录。
  3. 删除被拒绝时活动与报名记录保持不变。
- **基本事件流（编辑）**：
  1. 管理员在活动管理列表选择活动，点击“编辑”。
  2. 系统加载并显示活动当前值。
  3. 管理员修改字段并提交。
  4. 系统执行与 UC1 相同的字段校验，并追加：
     - 新容量不得小于当前“已通过”报名数；
     - 若活动存在有效报名（待审核/已通过），报名方式不得修改；
     - 新开始时间必须晚于当前时间。
  5. 系统保存修改，更新 `updated_at`。
  6. 系统提示“保存成功”，返回列表。
- **基本事件流（删除）**：
  1. 管理员在活动管理列表选择活动，点击“删除”。
  2. 系统检查该活动是否存在任何报名记录（含历史记录）。
  3. 若不存在，系统显示二次确认。
  4. 管理员确认后，系统删除活动。
  5. 系统提示“删除成功”，返回列表。
- **扩展事件流**：
  - **A-1 活动不存在**：提示“活动不存在或已被删除”，返回列表。
  - **A-2 新容量小于当前已通过数**：提示“容量不能小于当前已通过人数”，不保存。
  - **A-3 存在有效报名时修改报名方式**：提示“已有有效报名，不能修改报名方式”，不保存。
  - **A-4 新开始时间不晚于当前时间**：提示“开始时间必须晚于当前时间”，不保存。
  - **A-5 删除时存在报名记录**：拒绝删除，提示“该活动已有报名记录，不能删除；如需停办请等待后续版本提供取消/归档功能”。活动与记录保持不变。
  - **A-6 管理员取消二次确认**：不执行删除。
  - **A-7 并发编辑**：初始版本采用“最后写入生效”；若后续出现多管理员并发编辑，增加版本号乐观锁（见设计说明书扩展预案）。
  - **A-8 持久化失败**：事务回滚，提示“操作失败，请重试”。
- **补充约束**：
  - B-3 有报名记录的活动不做硬删除；本设计选择“拒绝删除并提示”，不选软删除（理由见设计说明书）。
  - B-4 容量只统计“已通过”；待审核不占名额，但容量下调后可能影响后续批准。
  - B-5 有效报名存在时不允许改报名方式；仅有历史记录（已取消/已拒绝）时允许修改。
  - D-2 活动字段见第 8 节。
- **设计提示（不在需求模型展开）**：删除策略与容量/报名方式约束需要“活动 + 报名”协同判断，设计阶段由应用服务协调，实体只负责自身状态判断。

### UC3 浏览/筛选活动

- **用例编号**：UC3
- **用例名称**：浏览/筛选活动
- **参与者**：学生（主要）
- **描述**：学生查看活动列表，按名称筛选，并选择活动进入详情。
- **触发器**：学生打开活动列表页，或输入名称关键词提交筛选。
- **前置条件**：
  1. 学生已进入学生端（固定演示账号）。
- **后置条件**：
  1. 页面显示符合条件的活动列表；不改变任何业务数据。
- **基本事件流**：
  1. 学生打开活动列表。
  2. 系统加载活动（未被删除），计算每个活动的已通过数、剩余名额与展示状态（报名中/已满/已开始）。
  3. 系统按开始时间升序显示活动卡片：名称、类型、开始时间、地点、容量、剩余名额、报名方式、状态。
  4. 学生可选输入名称关键词并提交。
  5. 系统按名称包含关键词过滤（中文按子串匹配；英文忽略大小写），重新显示列表。
  6. 学生选择一个活动，进入 UC3a 查看详情。
- **扩展事件流**：
  - **A-1 当前没有活动**：显示空状态“暂无活动”。
  - **A-2 筛选无匹配**：显示“未找到匹配活动”，保留关键词。
  - **A-3 列表与详情之间活动被删除**：进入详情时提示“活动不存在或已被删除”，返回列表。
  - **A-4 统计查询失败**：列表仍显示活动基本信息，剩余名额显示“—”，并提示“名额信息暂时不可用”。
- **补充约束**：
  - B-6 列表默认按开始时间升序；筛选只按名称，不扩展类型/时间/地点（需求只要求按名称）。
  - B-7 活动状态是展示状态，不是新的持久化状态字段：由 `start_at` 与当前时间、已通过数/容量计算。
  - N-2 列表在 200 条活动规模下可正常操作。
- **未包含**：分页、排序切换、按类型/时间/地点筛选（可作为后续扩展，不进入初始版本）。

### UC3a 查看活动详情

- **用例编号**：UC3a
- **用例名称**：查看活动详情
- **参与者**：学生（主要）
- **描述**：学生查看某一活动的完整信息、剩余名额、自己的报名状态与可执行操作。
- **触发器**：学生在活动列表点击某一活动。
- **前置条件**：
  1. 学生已进入学生端。
  2. 目标活动存在且未被删除。
- **后置条件**：
  1. 显示活动详情；不改变业务数据。
- **基本事件流**：
  1. 学生点击活动卡片。
  2. 系统加载活动详情、已通过数、待审核数（仅管理员可见？学生端只显示剩余名额）、当前学生在该活动上的有效报名（如有）。
  3. 系统显示：名称、类型、开始时间、地点、容量、剩余名额、报名方式、活动说明。
  4. 系统按当前状态显示操作按钮：
     - 可报名且无有效报名 → “报名”；
     - 有待审核/已通过报名 → “取消报名”与当前状态；
     - 活动已开始或名额已满 → 按钮禁用并说明原因。
- **扩展事件流**：
  - **A-1 活动不存在/已删除**：提示“活动不存在或已被删除”，返回列表。
  - **A-2 当前学生报名状态查询失败**：详情仍显示，报名按钮置灰并提示“报名状态暂时不可用”。
- **补充约束**：
  - B-8 学生端不显示其他学生的报名信息；待审核数只出现在管理员统计中。
  - B-9 “名额已满”以已通过数为准；待审核不占名额。
- **关系**：`«extend»` UC3，扩展点“学生选择某一活动”。

### UC4 提交报名

- **用例编号**：UC4
- **用例名称**：提交报名
- **参与者**：学生（主要）
- **描述**：学生对一个可报名活动提交报名；活动报名方式决定报名立即通过还是进入待审核。
- **触发器**：学生在活动详情点击“报名”。
- **前置条件**：
  1. 学生已进入学生端。
  2. 活动存在且未被删除。
  3. 当前时间早于活动开始时间。
- **后置条件**：
  1. 成功时恰好新增一条报名记录：
     - 直接报名 → 状态“已通过（APPROVED）”；
     - 审核型报名 → 状态“待审核（PENDING）”。
  2. 报名记录持久化；站内通知写入，或通知失败被记录。
  3. 失败时没有新增有效报名，原有数据不变。
- **基本事件流**：
  1. 学生在活动详情点击“报名”。
  2. 系统加载活动，检查活动存在、未删除、未开始。
  3. 系统检查该学生在该活动上是否已有“待审核/已通过”的有效报名。
  4. 系统统计该活动“已通过”报名数，检查是否小于容量。
  5. 系统根据活动报名方式确定初始状态：
     - 直接报名 → “已通过”；
     - 审核型报名 → “待审核”。
  6. 系统创建报名记录（生成 ID、状态、创建/更新时间）。
  7. 系统在写事务中保存报名记录。
  8. 事务提交后，系统发布“报名已提交”事件。
  9. 通知观察者写入站内消息（按事件键幂等）。
  10. 系统返回成功，页面显示：
      - 直接报名：“报名成功，已通过”；
      - 审核型：“报名已提交，等待管理员审核”。
- **扩展事件流**：
  - **A-1 活动不存在或已删除**：提示“活动不存在或已被删除”，用例结束。
  - **A-2 活动已开始**：提示“报名已截止”，用例结束。
  - **A-3 已存在有效报名**：提示“你已报名该活动，请勿重复提交”，用例结束。
  - **A-4 名额已满**：提示“名额已满”，用例结束；不创建报名。
  - **A-5 报名方式非法/未配置**：提示“活动报名方式配置错误”，记录日志，用例结束；不创建报名。
  - **A-6 并发重复提交**：后到的请求被“同一学生同一活动最多一条有效报名”的规则拒绝，按 A-3 处理；只保留一条有效报名。
  - **A-7 并发名额竞争**：写事务串行化，后到请求重新检查名额；若已满按 A-4 处理。
  - **A-8 通知写入失败**：记录失败日志（事件键、报名 ID、错误），报名记录保留，页面仍显示报名成功/已提交，并提示“通知稍后送达”。
  - **A-9 报名持久化失败**：事务回滚，提示“报名失败，请重试”，不产生半条记录。
- **补充约束**：
  - **B-10 公共规则与策略责任的划分**：活动可报名、无重复有效报名、名额未满、角色/归属正确属于公共规则，在报名业务协调处统一检查；报名方式只决定“初始状态是已通过还是待审核”，不重复实现公共规则。
  - B-11 名额只统计“已通过”；待审核不占名额。
  - B-12 同一学生同一活动最多一条有效报名；已取消/已拒绝保留历史，允许再次申请（生成新记录）。
  - B-13 通知在报名事务提交后发布；通知失败不回滚报名；按“报名 ID + 事件类型”幂等。
  - D-3 报名字段见第 8 节 D-3。
  - N-3 报名操作响应时间 ≤ 2 秒；并发提交不得突破容量。
- **两条备选流的说明**：
  - 直接报名与审核型报名不是两个用例，而是本用例按活动报名方式产生的两条结果路径。设计阶段再用策略抽象承载该变化点，公共规则留在报名业务协调处，不在需求模型里固化。
- **状态迁移**：
  - 直接报名：`(无) → 已通过`
  - 审核型报名：`(无) → 待审核`

### UC5 取消报名

- **用例编号**：UC5
- **用例名称**：取消报名
- **参与者**：学生（主要）
- **描述**：学生取消自己的一条“待审核”或“已通过”报名。
- **触发器**：学生在“我的报名”或活动详情点击“取消报名”。
- **前置条件**：
  1. 学生已进入学生端。
  2. 目标报名存在，且属于当前学生。
  3. 报名状态为“待审核”或“已通过”。
- **后置条件**：
  1. 成功时报名状态变为“已取消（CANCELLED）”，更新时间刷新。
  2. 若原状态为“已通过”，该名额释放；统计同步变化。
  3. 站内通知写入，或通知失败被记录。
- **基本事件流**：
  1. 学生打开“我的报名”列表。
  2. 系统列出该学生的报名：活动名称、报名时间、状态。
  3. 学生选择一条“待审核/已通过”报名，点击“取消报名”。
  4. 系统显示二次确认。
  5. 学生确认。
  6. 系统加载报名，校验归属与状态。
  7. 系统将状态改为“已取消”，刷新更新时间。
  8. 系统在写事务中保存。
  9. 事务提交后发布“报名已取消”事件，通知观察者写入站内消息。
  10. 系统提示“已取消”，刷新列表与活动剩余名额。
- **扩展事件流**：
  - **A-1 报名不存在**：提示“报名记录不存在”，刷新列表。
  - **A-2 报名不属于当前学生**：提示“无权操作该报名”，用例结束。
  - **A-3 状态不是待审核/已通过**：提示“该报名已处理，不能取消”，刷新列表。
  - **A-4 学生取消二次确认**：不改变状态。
  - **A-5 通知写入失败**：记录失败日志，取消结果保留。
  - **A-6 持久化失败**：事务回滚，提示“取消失败，请重试”，状态不变。
- **补充约束**：
  - B-14 取消不受活动开始时间限制；需求只限制“活动开始后不允许新增报名”。若后续业务要求活动开始后禁止取消，只需在报名业务协调处增加一条公共规则，不影响报名方式策略与通知结构（见假设 A-5）。
  - B-15 取消后名额按“已通过”数重新计算；待审核取消不释放名额（本来不占）。
  - D-3 报名字段见第 8 节。
- **状态迁移**：
  - `待审核 → 已取消`
  - `已通过 → 已取消`

### UC6 审批报名

- **用例编号**：UC6
- **用例名称**：审批报名
- **参与者**：管理员（主要）
- **描述**：管理员查看某活动的待审核报名，批准或拒绝；批准时再次检查名额。
- **触发器**：管理员在审批页选择一条待审核报名，点击“批准”或“拒绝”。
- **前置条件**：
  1. 管理员已进入管理端。
  2. 目标报名存在，状态为“待审核”。
- **后置条件**：
  1. 批准成功：报名状态变为“已通过”，占用一个名额；不得超出容量。
  2. 拒绝成功：报名状态变为“已拒绝”，不占名额。
  3. 站内通知写入，或通知失败被记录。
  4. 审批失败（名额已满/状态冲突）时报名状态不变。
- **基本事件流**：
  1. 管理员打开某活动的审批页。
  2. 系统列出该活动“待审核”报名：学生、提交时间。
  3. 管理员选择一条，点击“批准”或“拒绝”。
  4. 系统重新加载报名，检查状态仍为“待审核”。
  5. 若为“批准”：
     1. 系统加载活动，统计“已通过”数，检查是否小于容量。
     2. 名额充足时，将报名状态改为“已通过”，刷新更新时间。
     3. 保存并发布“报名已通过”事件，通知学生。
  6. 若为“拒绝”：
     1. 管理员可选填拒绝理由。
     2. 系统将报名状态改为“已拒绝”，刷新更新时间。
     3. 保存并发布“报名已拒绝”事件，通知学生（含理由）。
  7. 系统刷新待审核列表与统计。
- **扩展事件流**：
  - **A-1 报名不存在**：提示“报名记录不存在”，刷新列表。
  - **A-2 报名状态不是待审核**：提示“该申请已被处理”，刷新列表；不重复审批。
  - **A-3 批准时名额已满**：提示“名额已满，无法批准”，报名保持“待审核”；不超容量、不写通过通知。
  - **A-4 并发批准最后一个名额**：写事务串行化，只有一个成功；另一个按 A-3 处理。
  - **A-5 通知写入失败**：记录失败日志，审批结果保留。
  - **A-6 持久化失败**：事务回滚，提示“审批失败，请重试”，状态不变。
- **补充约束**：
  - B-16 批准时再次检查名额；这是最终防线，不能只依赖提交时的检查。
  - B-17 只有“待审核”可审批；已通过/已拒绝/已取消不得再次审批。
  - B-18 拒绝理由可选，写入通知内容；不新增独立字段（需求未要求）。
  - D-3 报名字段见第 8 节。
- **状态迁移**：
  - `待审核 → 已通过`（批准且名额充足）
  - `待审核 → 已拒绝`（拒绝）
  - 名额已满时保持 `待审核`（不迁移）

### UC7 查看报名统计

- **用例编号**：UC7
- **用例名称**：查看报名统计
- **参与者**：管理员（主要）
- **描述**：管理员按活动查看已通过数、待审核数与剩余名额。
- **触发器**：管理员在统计页选择活动，或从活动管理列表进入统计。
- **前置条件**：
  1. 管理员已进入管理端。
  2. 目标活动存在。
- **后置条件**：
  1. 显示统计结果；不改变业务数据。
- **基本事件流**：
  1. 管理员选择活动。
  2. 系统统计该活动“已通过”报名数。
  3. 系统统计该活动“待审核”报名数。
  4. 系统计算剩余名额 = `max(0, capacity - 已通过数)`。
  5. 系统显示：活动名称、容量、已通过数、待审核数、剩余名额。
- **扩展事件流**：
  - **A-1 活动不存在**：提示“活动不存在或已被删除”。
  - **A-2 统计查询失败**：显示“统计暂时不可用”，不影响活动与报名数据。
- **补充约束**：
  - B-19 剩余名额只由“已通过”计算；待审核不占名额。
  - B-20 初始版本只做单活动统计，不做跨活动汇总（P2-F08 只要求按活动）。
  - N-4 统计结果与报名列表在同一事务快照下读取，避免“已通过数 + 待审核数”与列表不一致（设计阶段落实）。

### UC8 查看站内通知

- **用例编号**：UC8
- **用例名称**：查看站内通知
- **参与者**：学生（主要）
- **描述**：学生查看自己的站内消息，了解报名/审批/取消结果，并将消息标记为已读。
- **触发器**：学生打开通知页，或点击某条通知。
- **前置条件**：
  1. 学生已进入学生端。
- **后置条件**：
  1. 显示该学生的消息列表；不改变报名/活动数据。
  2. 学生点击某条消息后，该消息 `is_read` 变为真。

  - **A-2 消息不存在或不属于当前学生**：提示“消息不存在”，刷新列表。

- **补充约束**：
  - B-21 学生只能查看自己的消息；管理员不通过本用例查看学生消息。
  - B-22 消息由 UC4/UC5/UC6 产生；本用例只读与标记已读，不创建消息。
  - D-4 消息字段见第 8 节。
- **未包含**：删除消息、批量已读、消息推送（邮件/短信）。

## 8. 数据需求

> 字段名采用设计阶段可映射的英文名；需求阶段只要求语义与约束。

### D-1 学生（Student）

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| student_id | String | 唯一、必填 | 学生 ID |
| name | String | 必填 | 姓名 |

### D-2 活动（Activity）

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| activity_id | String | 唯一、必填 | 活动 ID |
| title | String | 必填，1～100 字 | 活动名称 |
| category | String | 必填 | 活动类型 |
| start_at | DateTime | 必填，创建/编辑时晚于当前时间 | 开始时间 |
| location | String | 必填 | 地点 |
| capacity | int | 必填，> 0 | 人数上限 |
| policy_type | Enum | DIRECT / APPROVAL | 报名方式 |
| created_at | DateTime | 自动 | 创建时间 |
| updated_at | DateTime | 自动 | 更新时间 |

### D-3 报名（Registration）

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| registration_id | String | 唯一、必填 | 报名 ID |
| activity_id | String | 必填，引用 Activity | 活动 |
| student_id | String | 必填，引用 Student | 学生 |
| status | Enum | PENDING / APPROVED / REJECTED / CANCELLED | 状态 |
| created_at | DateTime | 自动 | 提交时间 |
| updated_at | DateTime | 自动 | 状态更新时间 |

**有效报名唯一性**：同一 `(activity_id, student_id)` 最多一条 `PENDING/APPROVED`；`CANCELLED/REJECTED` 不限制条数。

### D-4 站内消息（Message）

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| message_id | String | 唯一、必填 | 消息 ID |
| student_id | String | 必填，引用 Student | 接收学生 |
| activity_id | String | 必填，引用 Activity | 关联活动 |
| content | String | 必填 | 消息内容 |
| created_at | DateTime | 自动 | 创建时间 |
| is_read | bool | 默认 false | 是否已读 |
| event_key | String | 唯一、必填 | 幂等键：`registration_id:event_type`（设计阶段新增，见设计说明书） |

### D-5 枚举

- 报名状态：`PENDING`（待审核）、`APPROVED`（已通过）、`REJECTED`（已拒绝）、`CANCELLED`（已取消）。
- 报名方式：`DIRECT`（直接报名）、`APPROVAL`（审核型报名）。
- `RegistrationEventType`：`SUBMITTED`、`APPROVED`、`REJECTED`、`CANCELLED`。

| A-8 | 活动列表按开始时间升序；筛选只按名称子串。 | UC3 范围。 |
| A-9 | 拒绝理由可选，写入消息内容，不新增字段。 | UC6/D-4。 |
| A-10 | 时间使用服务器本地时间，ISO-8601 格式；演示环境不处理时区。 | 日期比较与展示。 |
| A-11 | 打开通知列表不自动全部已读；点击单条才标记已读。 | UC8。 |
| A-12 | 同一学生同一活动可保留多条历史记录，但最多一条有效记录。 | 唯一约束与再次申请。 |

> 编号说明：各用例“扩展事件流”里的 A-n 是**用例局部编号**；本节 A-n 是**全局假设**。设计文档引用局部流时写 `UC4-A3`，引用全局假设时写“假设 A-3”，避免混淆。

**待确认项（不阻塞初始版本，但需在评审时记录）：**

1. 活动开始后是否允许取消报名？本规格按 A-5 允许；若教师要求禁止，增加一条公共规则即可。
2. 审核型活动在名额已满时是否还允许提交待审核申请？本规格选择“不允许”，提交时即检查名额；若希望保留候补，需要新增候补状态/用例。
3. 删除活动是否要保留历史？本规格选择拒绝删除；若要求软删除，需要增加 `deleted_at` 并修改所有查询。
4. 是否需要管理员查看学生通知？当前只做学生通知；管理员操作结果通过管理端提示反馈。

## 11. 验收用例映射（C1～C10）

| 验收编号 | 场景 | 覆盖用例 | 预期 |
|---|---|---|---|

| C10 | 重启服务后查询活动、报名、通知 | 持久化（N-6） | 数据仍一致。 |

**补充边界用例（设计/测试阶段展开）：**

- E1 活动已开始后报名 → UC4-A2。
- E2 并发两名学生抢最后一个名额 → UC4-A7 / N-3。
- E3 两名管理员同时批准最后一个名额 → UC6-A4 / N-3。
- E4 通知写入抛异常 → UC4-A8 / UC6-A5 / N-5。
- E5 删除有报名的活动 → UC2-A5。
- E6 修改有有效报名的活动报名方式 → UC2-A3。
- E7 容量下调到小于已通过数 → UC2-A2。
- E8 学生取消他人报名 → UC5-A2。
- E9 已拒绝/已取消后再次申请 → UC4 基本流 + B-7。
- E10 审批已处理报名 → UC6-A2。
