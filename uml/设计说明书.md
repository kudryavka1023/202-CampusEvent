## 第 1 部分 引言

### 1.1 编写目的

本文档把实验二的初始需求（P2-F01～P2-F08）转化为可实现、可测试、可评审的设计基线，回答四个问题：

1. 系统分成哪些层与子系统，依赖方向是什么。
2. 每个用例由哪些类协作完成，类的职责、属性、方法签名是什么。
3. 报名策略、通知解耦、名额并发、事务边界、删除策略如何落地。
4. 设计如何追溯到需求与验收用例，未来变更会改哪些类、成本多大。

本文档**不包含**应用代码、部署脚本与最终数据库迁移脚本；这些在评审通过后按本设计实现。

### 1.2 命名规范

| 对象 | 规范 | 示例 |
|---|---|---|
| 类 / 接口 | PascalCase，英文名词；接口不加 `I` 前缀 | `RegistrationService`、`RegistrationPolicy` |
| 属性 / 方法 | camelCase，动词开头的方法表示行为 | `approvedCount`、`hasCapacity()` |
| 枚举 | PascalCase 类型名；成员 UPPER_SNAKE | `RegistrationStatus.APPROVED` |

| 错误码 | UPPER_SNAKE | `SEATS_FULL`、`DUPLICATE_ACTIVE` |
| 图件 | 两位序号 + 场景名 | `07-提交报名-sequence.drawio` |
| 时间 | ISO-8601 本地时间（假设 A-10） | `2026-11-22T14:30:00` |

### 1.3 术语定义

| 术语 | 含义 |
|---|---|
| 有效报名 | 状态为 `PENDING` 或 `APPROVED` 的报名；同一学生同一活动最多一条。 |
| 历史报名 | 状态为 `REJECTED` 或 `CANCELLED` 的报名；保留记录，允许再次申请。 |
| 公共规则 | 与报名方式无关的规则：活动存在/未开始、无重复有效报名、年级符合（CR-01）、名额未满、角色与归属正确。 |
| 报名策略 | 只决定“提交后初始状态是 `APPROVED` 还是 `PENDING`”的抽象。 |
| 资格规则（CR-01） | 判断“是否允许报名”的可组合约束；年级规则返回 `EligibilityViolation`，不创建报名。 |
| 领域事件 | 表示“报名已提交/已通过/已拒绝/已取消”的不可变事实，供通知观察者消费。 |
| 幂等键 | `eventKey = registrationId + ":" + eventType`，保证同一事件不重复写消息/邮件记录。 |
| 模拟邮件（CR-02） | 不接 SMTP 的本地发送器；只写 `email_log`，记录收件人、主题、内容、状态与时间。 |
| Repository | 聚合的持久化接口；领域层只依赖接口，SQLite 实现在基础设施层。 |
| 工作单元（UoW） | 一次写事务的边界；本设计用 `BEGIN IMMEDIATE ... COMMIT/ROLLBACK` 实现。 |
| 部分唯一索引 | 只对满足 `WHERE` 条件的行生效的唯一索引；用于“有效报名唯一、历史可多条”。 |
| DTO / 值对象 | 跨层传递的只读数据载体，如 `RegistrationResult`、`ActivitySummary`。 |

## 第 2 部分 总体设计

### 2.1 硬件运行环境

| 环境 | 最低配置 | 说明 |
|---|---|---|
| 开发机 | 4 核 / 8 GB / 20 GB 磁盘 | Windows 11 或 Linux；用于编码、单元测试、演示。 |
| 演示服务器 | 1 vCPU / 1 GB / 10 GB 磁盘 | 单实例部署；SQLite 与日志放本地磁盘。 |
| 网络 | 校园网或公网可访问 | 仅 HTTP/HTTPS，无外部消息中间件。 |

### 2.2 软件运行环境

| 项 | 选择 | 理由 |
|---|---|---|
| 语言 | Python 3.11+ | 课程熟悉；类型标注与 `dataclass` 足够表达设计。 |
| Web 框架 | Flask 3.x | 轻量、路由清晰；不引入重型 ORM 与自动迁移。 |
| 模板 | Jinja2 | 服务端渲染，减少前后端分离的额外复杂度。 |
| 数据库 | SQLite 3.35+ | 单文件、零运维；支持部分唯一索引与 WAL。 |
| 测试 | pytest | 单元、服务、仓储、接口测试统一。 |
| 部署 | gunicorn（Linux）/ waitress（Windows） | 单进程多线程；SQLite 写事务串行化。 |
| 日志 | Python `logging` + 文件 | 通知失败写 `logs/notification-failure.log`。 |

**明确不引入**：Redis、RabbitMQ/Kafka、微服务、ORM 自动迁移、前端框架。理由是初始版本规模小、单机部署、课程周期有限；这些技术会放大部署与调试成本，而不解决当前的核心设计问题。

### 2.3 系统架构与依赖方向

系统采用**分层单体**，共四层：

```text
┌──────────────────────────────────────────────────────────────┐
│ 界面层（boundary）                                            │
│ ActivityController  RegistrationController  ApprovalController│
│ NotificationController  StatisticsController  Jinja2 模板     │
└───────────────────────────┬──────────────────────────────────┘
                            │ 只调用应用服务
┌───────────────────────────▼──────────────────────────────────┐
│ 应用服务层（control）                                          │
│ ActivityService  RegistrationService                          │
│ StatisticsService  NotificationQueryService                   │
└───────────────────────────┬──────────────────────────────────┘
                            │ 依赖领域对象与接口
┌───────────────────────────▼──────────────────────────────────┐
│ 领域层（entity / value / policy / event）                      │
│ Student  Activity  Registration  Message                      │
│ RegistrationPolicy + 两个实现 + Factory                        │
│ RegistrationEvent  RegistrationResult  ActivitySummary ...     │
└───────────────────────────▲──────────────────────────────────┘
                            │ 实现接口（依赖倒置）
┌───────────────────────────┴──────────────────────────────────┐
│ 基础设施层（infrastructure）                                   │
│ Sqlite*Repository  SimpleRegistrationEventPublisher            │
│ MessageNotificationObserver  NotificationFailureLogger         │
│ 事务管理器  SQLite 连接与迁移脚本                               │
└──────────────────────────────────────────────────────────────┘
```

**依赖规则：**

1. 界面层只能调用应用服务，不直接访问 Repository，不写业务规则。
2. 应用服务依赖领域对象、Repository 接口与 `TransactionManager` 接口；不依赖 Flask、SQLite、具体 SQL。
3. 领域层不依赖任何外层；实体只做自身状态判断，不查数据库。
4. 基础设施层实现接口，在组合根（应用启动处）注入。
5. 依赖方向永远指向内层；`SqliteRegistrationRepository` 可以依赖 `RegistrationRepository`，反之不行。

**读图说明：**

- `06-design-class-architecture.drawio` 画的是“谁调用谁、接口在哪、依赖往哪指”，适合看分层与替换点。
- `06-design-class.drawio` 画的是“领域里有哪些概念、策略与事件如何组织”，适合看业务规则与模式。
- 两张图共用的类名、方法名完全一致；架构图不重复画实体属性，避免一张图过载。
- 架构图为图面可读，`List`/`Optional` 省略元素类型；完整签名以 7.3 节为准（如 `List<ActivitySummary>`、`List<RegistrationSummary>`）。

#### 2.3.1 分析类到设计类的映射（为什么拆 / 合）

分析模型（`03-analysis-class.drawio`）用业务词汇表达“需要哪些职责”；设计模型再决定“用哪些类、接口和技术实现”。两者不是一一对应，差异如下：

| 分析类 | 设计类 | 处理 | 理由 |
|---|---|---|---|
| 活动管理页面、活动浏览页面 | `ActivityController` | 合并 | 两者都是活动相关的 Web 适配器，路由与表单绑定高度重合；合并后按方法区分 `list/detail/create/update/delete`。 |
| 报名页面 | `RegistrationController` | 保留 | 报名/取消/我的报名共享学生会话与归属校验。 |
| 审批页面 | `ApprovalController` | 保留（变薄） | 只做参数绑定与 `decision` 映射；事务与状态校验下沉到 `RegistrationService.review`。 |
| 统计页面 | `StatisticsController` | 保留 | 只调用 `StatisticsService`，不拼 SQL。 |
| 通知页面 | `NotificationController` | 保留 | 查询与已读标记；不承担事件写入。 |
| 活动管理控制器 | `ActivityService` + `Activity` | 拆分 | 用例协调（校验字段、删除前查报名）放服务；“是否可报名/容量/剩余名额”放实体，避免贫血模型。 |
| 浏览活动控制器 | `ActivityService` + `ActivitySummary` | 拆分 | 查询协调放服务；列表所需的聚合计数与展示状态放只读值对象，避免实体承担查询职责。 |
| 报名控制器 | `RegistrationService` + `RegistrationPolicy` + `RegistrationPolicyFactory` | 拆分 | 公共规则（活动状态、重复、名额）留在服务；唯一随报名方式变化的“初始状态”抽成策略，满足 OCP。 |
| 审批控制器 | `RegistrationService.review` + `ApprovalController` | 行为合并 + 控制器变薄 | 批准/拒绝与报名共用同一事务、状态校验和事件发布；控制器保留，只把按钮映射为 `decision`，业务合并到 `review`。 |
| 统计控制器 | `StatisticsService` + `ActivityStatistics` | 拆分 | 聚合查询与页面渲染分离；统计结果用值对象保证“已通过/待审核/剩余”同快照。 |
| 通知控制器 | `NotificationQueryService` + `MessageNotificationObserver` | 拆分 | 读（查消息/标记已读）与写（事件副作用）职责不同；观察者只负责把事件落成消息。 |
| `Student`、`Activity`、`Registration`、`Message` | 同名设计类 | 保留并加方法 | 分析阶段已识别出实体；设计阶段补充状态迁移、容量判断、幂等键等行为。 |
| （分析阶段没有） | `RegistrationEvent`、`RegistrationContext`、`RegistrationResult`、`ActivityResult`、`ActivitySummary`、`ActivityStatistics`、`RegistrationSummary` | 新增 | 为解耦、幂等、跨层结果传递、审批读模型而引入的值对象；不改变业务概念，只降低参数耦合与异常穿透。 |
| （分析阶段没有） | `RegistrationEventPublisher`、`RegistrationObserver`、`SimpleRegistrationEventPublisher` | 新增 | 通知解耦的设计机制；分析阶段只写“报名后通知学生”这一职责，不固化实现。 |

**结论：** 设计类数量增加主要来自三处：控制器按角色/页面细分、服务按用例族拆分、策略/事件/值对象等设计机制。实体没有被拆散，保证业务概念稳定；新增类都围绕“变化点隔离”，不是为了模式数量。

### 2.5 关键设计决策摘要

| 编号 | 问题 | 备选 | 选择 | 理由 | 成本 |
|---|---|---|---|---|---|
| D-01 | 系统形态 | 微服务 / 分层单体 | 分层单体 | 规模小、单机部署、事务简单；微服务会引入网络与分布式事务成本。 | 未来水平扩展需改架构。 |
| D-02 | 报名方式差异 | 主流程 `if/else` / 继承 / 策略 | 策略 + 工厂 | 新增抽签/候补只加类，不改主流程；符合 OCP。 | 多 4 个类（接口 + 2 实现 + 工厂）与一次工厂查找。 |
| D-03 | 公共规则放哪 | 每个策略各写一遍 / 服务统一 | `RegistrationService` + `Activity` | 名额、重复、活动状态与报名方式无关；放策略会重复且易分叉。 | 服务方法较长，需要清晰的私有校验方法。 |
| D-04 | 通知解耦 | 服务直接写消息 / 观察者 / 消息队列 | 观察者（进程内） | 满足解耦与可测试性；不引入 MQ 运维。 | 同步调用增加一次写库延迟；崩溃窗口需说明。 |
| D-05 | 通知失败 | 回滚报名 / 忽略 / 记录日志 | 记录日志、不回滚 | 报名是主业务，通知是副作用；不能因通知失败丢报名。 | 需要日志与人工补偿预案。 |
| D-06 | 并发名额 | 先查后写 / 数据库锁 / 唯一索引 | `BEGIN IMMEDIATE` + 部分唯一索引 | SQLite 单写者串行化，检查与写入原子；唯一索引兜底重复。 | 写吞吐受限，不能多实例同时写。 |
| D-07 | 删除有报名的活动 | 硬删除 / 软删除 / 拒绝 | 拒绝并提示 | 保留历史、查询简单、无 `deleted_at` 过滤风险。 | 管理员不能删除已有报名的活动，需后续归档功能。 |
| D-08 | 批准/拒绝接口 | 两个方法各自重复校验 / 一个 `review` | `review(decision)` | 事务、状态校验、事件发布只写一次；`decision` 只影响迁移分支。 | 控制器需把两个按钮映射为枚举。 |

## 第 3 部分 数据库设计

### 3.1 表名列表

| 表 | 作用 | 主要访问者 |
|---|---|---|
| `students` | 学生身份 | `StudentRepository`、登录演示 |
| `activities` | 活动 | `ActivityRepository` |
| `registrations` | 报名记录 | `RegistrationRepository` |
| `messages` | 站内消息 | `MessageRepository` |
| `email_log`（CR-02） | 模拟邮件发送记录 | `EmailLogRepository` |

### 3.2 表关系

```text
students 1 ──────< registrations >────── 1 activities
students 1 ──────< messages      >────── 1 activities
students 1 ──────< email_log     >────── 0..1 报名事件
```

- 一个学生有多条报名；一个活动有多条报名。
- 一个学生有多条消息；一个活动可关联多条消息。
- 一个学生有多条邮件记录；每条记录关联一条报名与一个业务事件（`event_key` 唯一）。
- `email_log` 不建到 `activities` 的外键，活动信息通过报名关联；避免活动删除与历史邮件记录冲突。
- `registrations` 对 `activities`、`students` 使用 `ON DELETE RESTRICT`：有报名时禁止删除活动/学生。
- `messages` 对 `activities`、`students` 使用 `ON DELETE RESTRICT`：消息是历史证据，不随活动硬删除。

### 3.3 表结构

### 3.4 约束、索引与 DDL 要点

```sql
PRAGMA foreign_keys = ON;
PRAGMA journal_mode = WAL;
PRAGMA busy_timeout = 5000;

CREATE UNIQUE INDEX ux_registration_active
  ON registrations(activity_id, student_id)
  WHERE status IN ('PENDING', 'APPROVED');

CREATE INDEX ix_registration_activity_status
  ON registrations(activity_id, status);

CREATE INDEX ix_registration_student_created
  ON registrations(student_id, created_at DESC);

CREATE INDEX ix_message_student_created
  ON messages(student_id, created_at DESC);

-- CR-02
CREATE UNIQUE INDEX ux_email_log_event_key ON email_log(event_key);
CREATE INDEX ix_email_log_created ON email_log(created_at DESC);
```

**关键点：**

1. `ux_registration_active` 是“同一学生同一活动最多一条有效报名”的最终防线；历史记录（`REJECTED`/`CANCELLED`）不受限制。
2. `messages.event_key` 与 `email_log.event_key` 唯一，保证通知/邮件幂等；重复事件插入会抛 `IntegrityError`，观察者按“已通知/已发送”处理。
3. `CHECK` 约束把状态、报名方式、年级与邮件状态限制在枚举内；应用层校验之外再加数据库兜底。
4. `ON DELETE RESTRICT` 与“拒绝删除有报名的活动”策略一致，防止绕过服务层直接删库造成孤儿记录。
5. 时间用 TEXT 存 ISO-8601，排序与比较按字典序即可；演示环境不处理时区（假设 A-10）。

### 3.6 事务边界

| 操作 | 事务 | 覆盖范围 | 事件发布时机 |
|---|---|---|---|
| `submit` | `BEGIN IMMEDIATE` | 加载活动/学生 → 校验 → 查重 → 资格规则 → 计数 → 建记录 → 保存 | `COMMIT` 之后 |
| `review`（批准/拒绝） | `BEGIN IMMEDIATE` | 加载报名 → 状态校验 → 批准时复查名额 → 迁移 → 更新 | `COMMIT` 之后 |
| `cancel` | `BEGIN IMMEDIATE` | 加载报名 → 归属/状态校验 → 迁移 → 更新 | `COMMIT` 之后 |
| `create/update/delete` 活动 | `BEGIN IMMEDIATE` | 校验 → 保存/更新/删除 | 无领域事件 |
| 通知写消息 | 独立短事务 | `existsByEventKey` → `save(message)` | 由观察者内部完成 |
| 模拟邮件记录（CR-02） | 独立短事务 | `existsByEventKey` → `send(EmailMessage)` → `save(emailLog)`；失败先写 `FAILED` 再抛出 | 由观察者内部完成 |

**为什么用 `BEGIN IMMEDIATE` 而不是默认的延迟事务：**

- SQLite 默认 `BEGIN` 是 deferred：先读后写时，写锁在升级阶段才获取，两个并发写可能一个失败为 `SQLITE_BUSY`，或出现“都读到未满、都尝试写”的竞争。
- `BEGIN IMMEDIATE` 在事务开始就获取写锁，后续“计数 + 插入”是串行的；第二个请求会等待（`busy_timeout`），拿到锁后重新看到最新计数。
- 代价：所有写操作串行，吞吐受限；对课程规模（单活动几十到几百人）足够。未来换 PostgreSQL 时，改用行锁/唯一索引 + `SERIALIZABLE` 或 `SELECT ... FOR UPDATE`。

**通知与事务的关系：**

1. 报名/审批/取消先提交事务，再 `publish`；通知失败不回滚。
2. 观察者写消息使用独立事务；`event_key` 唯一约束保证重复事件不会重复写。
3. 若进程在 `COMMIT` 与 `publish` 之间崩溃，通知会丢失且没有失败日志。这是“双写”残留风险；初始版本用“启动时补偿脚本”兜底（扫描无消息的有效报名并补发），变更版可改为事务性 Outbox（见第 12 部分）。

### 3.7 持久化与重启一致性（C10）

- SQLite 文件放在 `data/campus_event.db`，WAL 模式；正常关闭时执行 `PRAGMA wal_checkpoint(TRUNCATE)`。
- 应用启动时执行 `PRAGMA foreign_keys = ON`，并运行幂等的建表/索引脚本。
- 重启后活动、报名、消息从同一数据库恢复；`ActivitySummary` 与统计是查询结果，不缓存，因此不会出现缓存与库不一致。
- 备份：`sqlite3 data/campus_event.db ".backup backup/campus_event-YYYYMMDD.db"`；演示前与验收后各备份一次。

### 4.1 活动管理子系统（UC1、UC2）

#### 4.1.1 类设计

| 类 | 职责 | 关键方法 |
|---|---|---|
| `ActivityController` | 绑定表单、校验管理员会话、调用服务、渲染结果 | `create`、`update`、`delete`、`list`、`detail` |
| `ActivityService` | 活动用例协调；容量/报名方式/时间约束；删除前检查报名 | `create`、`update`、`delete`、`findById`、`search` |
| `Activity` | 活动自身状态判断；不查库 | `isOpen`、`hasCapacity`、`remainingSeats`、`canChangePolicy` |
| `ActivityRepository` | 活动持久化接口 | `findById`、`searchSummaries`、`save`、`update`、`delete` |

**为什么控制器不直接查 Repository：** 控制器只做输入/输出适配；把“容量不得小于已通过数”“有有效报名不得改报名方式”放在服务层，才能被接口测试直接覆盖，也避免 Web 层与 SQL 耦合。

#### 4.1.2 创建活动（UC1）走查

1. `ActivityController.create(adminId, activity)` 校验会话角色为 `ADMIN`，把表单绑定为 `Activity` 草稿。
2. `ActivityService.create(adminId, activity)`：
   - 校验 `title` 非空且 ≤100 字、`category`/`location` 非空；
   - `capacity > 0`；`startAt > now`；`policyType ∈ {DIRECT, APPROVAL}`；
   - 生成 `activityId`；`createdAt`/`updatedAt` 由仓储在 `save` 时写入，不进入实体；
   - `activityRepository.save(activity)`。
3. 成功返回 `ActivityResult.success(activity)`；失败返回带 `errorCode` 的结果，控制器渲染字段错误。

**失败分支：** 必填缺失/格式错误 → `VALIDATION_ERROR`；容量 ≤0 → `VALIDATION_ERROR`；开始时间不晚于当前 → `VALIDATION_ERROR`；持久化异常 → 回滚并返回 `PERSISTENCE_ERROR`。

#### 4.1.3 编辑与删除（UC2）走查

| 步骤 | 编辑 | 删除 |
|---|---|---|
| 1 | 加载活动，不存在 → `NOT_FOUND` | 加载活动，不存在 → `NOT_FOUND` |
| 2 | 校验字段（同 UC1） | `registrationRepository.existsByActivity(activityId)` |
| 3 | 若容量下调：`newCapacity >= countByActivityAndStatus(APPROVED)`，否则 `CAPACITY_BELOW_APPROVED` | 若存在任何报名（含历史）→ `ACTIVITY_HAS_REGISTRATIONS`，拒绝删除 |
| 4 | 若存在有效报名（`PENDING/APPROVED`）且 `policyType` 改变 → `POLICY_IMMUTABLE`（`Activity.canChangePolicy(hasActive)` 为假） | 不存在报名 → 二次确认后 `activityRepository.delete` |
| 5 | 保存；仓储更新 `updated_at` | 返回成功；列表刷新 |

**删除策略决策：**

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 硬删除（有报名也删） | 实现最简单 | 丢历史、孤儿报名、统计失真 | 否决 |
| 软删除 `deleted_at` | 保留历史、可恢复 | 所有查询都要过滤；唯一索引/统计/详情都要改；容易漏 | 初始版本不选 |
| 拒绝删除并提示 | 无 schema 改动、历史完整、查询简单 | 管理员不能清理已有报名的活动 | **选择**（假设 A-3） |

未来若需要“停办/归档”，新增 `archived_at` 与“归档”用例，而不是把删除改成软删除；这样语义更清晰，影响面可评估。

> 本子系统未单独出顺序图：交互是“控制器 → 服务 → 仓储”的直线调用，没有跨对象协作或复杂片段；用上表走查替代，避免为 CRUD 画低信息量的图。关键交互图集中在报名与审批。

#### 4.2.2 提交报名顺序图（`07-提交报名-sequence.drawio`）

> 流程总览见 `10-activity-报名流程.drawio`：先判定公共规则（活动可报名 → 无重复 → 年级符合 → 名额未满），再按报名方式分流，最后汇合到保存、事件、站内消息 + 模拟邮件。活动图用于看“判定顺序与失败出口”，顺序图用于看“对象协作与事务边界”。

**读图顺序：**

1. 学生 → `RegistrationController.submit(activityId)`；控制器 → `RegistrationService.submit(studentId, activityId)`。
2. 服务开启写事务，加载活动、判断 `isOpen`、查有效报名、加载学生、统计已通过数、执行资格规则、判断 `hasCapacity`。
3. 外层 `alt [已存在有效报名] / [无重复]`：重复直接返回 `DUPLICATE_ACTIVE`。
4. 年级分支 `alt [年级不符] / [年级符合]`：返回 `GRADE_NOT_ALLOWED`，不创建报名（CR-01）。
5. 内层 `alt [名额已满] / [名额充足]`：满员返回 `SEATS_FULL`。
6. 策略分支 `alt [policyType = DIRECT] / [APPROVAL]`：工厂取策略，策略只返回 `APPROVED` 或 `PENDING`。
7. 合并后创建 `Registration`、`save`、提交事务。
8. 事务外 `publish(RegistrationEvent)`；图中 EP 是 `RegistrationEventPublisher` 接口，运行时实现为 `SimpleRegistrationEventPublisher`，负责遍历观察者、捕获异常并写失败日志。站内消息与模拟邮件两个观察者都按 `eventKey` 幂等。
9. `opt [邮件发送失败]`：邮件观察者先写 `FAILED` 记录，再抛异常；发布者捕获后调用 `NotificationFailureLogger.log(event, error)`，报名保持有效。
10. `opt [任一观察者抛异常]`：发布者捕获异常、写日志，继续调用其他观察者。
11. 返回 `success(registration)`，控制器显示“已通过/待审核”。

**策略责任边界（设计任务 B 的结论）：**

| 规则 | 放在哪 | 为什么 |
|---|---|---|
| 活动存在/未开始 | `Activity.isOpen` + 服务 | 与报名方式无关；实体最了解自己的时间。 |
| 无重复有效报名 | `RegistrationService` + 唯一索引 | 需要跨记录查询；数据库兜底并发。 |
| 年级符合（CR-01） | `CompositeEligibilityRule` + `GradeEligibilityRule` | 与报名方式无关；可作为独立规则组合、单测，不塞进策略。 |
| 名额未满 | `RegistrationService` + `Activity.hasCapacity` | 需要聚合计数；两种报名方式共用。 |
| 初始状态 | `RegistrationPolicy` | 唯一随报名方式变化的点。 |
| 是否需要审批 | 由初始状态 `PENDING` 隐含 | 不额外加布尔字段，避免状态与标志不一致。 |

#### 4.2.3 取消报名顺序图（`07-取消报名-sequence.drawio`）

1. 学生 → `RegistrationController.cancel(registrationId)`；控制器 → `RegistrationService.cancel(studentId, registrationId)`。
2. 服务加载报名，校验 `isOwnedBy(studentId)` 与 `isActive()`。
3. `alt [不存在/非本人/状态不允许]` → `failure(errorCode)`。
4. `else [可取消]`：`Registration.cancel()` → `update` → `publish(CANCELLED)` → 观察者写消息 → `success`。
5. 控制器刷新“我的报名”与活动剩余名额。

**边界：** 取消不检查活动是否开始（假设 A-5）；原状态为 `APPROVED` 时释放名额，`PENDING` 取消不释放（本来不占）。

#### 4.2.4 状态机（`09-state.drawio`）

| 当前状态 | 事件 | 守卫 | 新状态 | 副作用 |
|---|---|---|---|---|
| （无） | 提交报名 | `policyType=DIRECT` | `APPROVED` | 占 1 个名额；发 `SUBMITTED` 事件 |
| （无） | 提交报名 | `policyType=APPROVAL` | `PENDING` | 不占名额；发 `SUBMITTED` 事件 |
| `PENDING` | 批准 | 名额充足 | `APPROVED` | 占名额；发 `APPROVED` 事件 |
| `PENDING` | 批准 | 名额已满 | `PENDING` | 不迁移；返回 `SEATS_FULL` |
| `PENDING` | 拒绝 | 无 | `REJECTED` | 发 `REJECTED` 事件（含理由） |
| `PENDING` | 学生取消 | 本人 | `CANCELLED` | 发 `CANCELLED` 事件 |
| `APPROVED` | 学生取消 | 本人 | `CANCELLED` | 释放名额；发 `CANCELLED` 事件 |
| `REJECTED` / `CANCELLED` | 再次申请 | 无 | 新建记录 | 旧记录不改；新记录从初始状态开始 |

**状态一致性：** `RegistrationStatus` 的四个枚举值与数据库 `CHECK`、状态图、顺序图中的字符串完全一致；`Registration.approve/reject/cancel` 内部先判断当前状态，非法迁移抛领域异常，由服务层转为 `ALREADY_HANDLED` / `INVALID_STATE`（按用例）。

### 4.3 审批子系统（UC6）

#### 4.3.1 类设计

| 类 | 职责 | 关键方法 |
|---|---|---|
| `ApprovalController` | 待审核列表、批准/拒绝按钮、管理员会话 | `pendingList`、`approve`、`reject` |
| `RegistrationService` | 审批事务、状态校验、批准时复查名额、待审核列表、事件发布 | `review`、`listPending` |
| `Registration` | 状态迁移 | `isPending`（由 `status` 判断）、`approve`、`reject` |
| `RegistrationSummary` | 报名列表的只读读模型（含学生姓名/活动名称） | `isPending` |
| `Activity` | 名额判断 | `hasCapacity` |
| `RegistrationRepository` | 加载/更新/计数/待审核列表 | `findById`、`update`、`countByActivityAndStatus`、`findByActivityAndStatus` |
| `ActivityRepository` | 加载活动 | `findById` |
| `RegistrationEventPublisher` | 发布审批结果事件 | `publish` |

**为什么列表用 `RegistrationSummary`：** 页面需要“学生姓名/活动名称 + 提交时间 + 状态”，而 `Registration` 只有 `studentId`/`activityId`。让 `RegistrationRepository.findByActivityAndStatus` 与 `findByStudent` 用一条 JOIN 查询返回读模型，避免控制器逐条查学生/活动（N+1），也避免把 `StudentRepository` 注入审批服务。读模型不参与状态迁移，只用于展示。

**为什么用 `review(decision)` 而不是 `approve`/`reject` 两个服务方法：**

- 两个方法的“加载 → 状态校验 → 事务 → 发布”完全相同，只有迁移分支不同；复制会产生两套容易分叉的边界处理。
- `ApprovalDecision` 枚举把“用户选择”显式化，控制器只负责把按钮映射为 `APPROVE`/`REJECT`。
- 未来加“批量审批/撤销审批”时，可以在 `review` 外层复用，而不必改两个方法。
- 成本：控制器多一个枚举映射；服务方法多一个参数。

#### 4.3.2 审批顺序图（`07-审批报名-sequence.drawio`）

1. 管理员打开审批页 → `ApprovalController.pendingList(adminId, activityId)` → `RegistrationService.listPending(activityId)`；服务先 `ActivityRepository.findById` 确认活动存在（不存在 → `NOT_FOUND`），再 `RegistrationRepository.findByActivityAndStatus(activityId, PENDING)`，返回带学生姓名与活动名称的 `RegistrationSummary` 列表。
2. 管理员点击批准/拒绝 → `ApprovalController` 绑定 `decision` 与可选 `reason`。
3. 控制器 → `RegistrationService.review(adminId, registrationId, decision, reason)`。
4. 服务加载报名，`isPending()`；非待审核 → `ALREADY_HANDLED`。
5. `alt [decision = APPROVE]`：
   - 加载活动，统计已通过数，`hasCapacity`；
   - `alt [名额已满]` → `SEATS_FULL`，保持 `PENDING`；
   - `else [名额充足]` → `Registration.approve()` → `update` → `publish(APPROVED)` → 站内消息 + 模拟邮件 → `success`。
6. `else [decision = REJECT]`：`Registration.reject()` → `update` → `publish(REJECTED)` → 站内消息 + 模拟邮件（含理由）→ `success`。
7. 邮件失败只影响 `email_log` 状态与失败日志，不改变审批结果。
7. 控制器刷新待审核列表与统计。

**C8 / E3 的落点：** 批准分支的名额复查是最终防线；`BEGIN IMMEDIATE` 保证两个管理员同时批准最后一个名额时只有一个成功，另一个看到 `approvedCount == capacity` 并返回 `SEATS_FULL`。

### 4.4 通知子系统（UC8 + 事件副作用）

#### 4.4.1 事件类型与消息内容

| 事件类型 | 触发 | 消息内容示例 | 备注 |
|---|---|---|---|
| `SUBMITTED` | 报名成功（直接或审核型） | “报名已提交，当前状态：已通过。” / “报名已提交，等待审核。” | 直接型也发；仅直接型另发模拟邮件（CR-02） |
| `APPROVED` | 管理员批准 | “你报名的活动已通过审核。” | 只在批准成功后发；站内消息 + 模拟邮件 |
| `REJECTED` | 管理员拒绝 | “你报名的活动未通过。理由：名额调整。” | 理由可选；站内消息 + 模拟邮件 |
| `CANCELLED` | 学生取消 | “你已取消报名。” | 释放名额；只发站内消息，不发邮件 |

**为什么消息正文不写活动标题：** `RegistrationEvent` 只携带通知所需的最小事实（ID、状态、理由）；通知页用 `activity_id` 生成活动链接，避免事件复制展示字段、活动改名后消息与活动不一致。

#### 4.4.2 观察者链路

```text
RegistrationService
  └─ publish(event)                 // 事务提交后
       └─ SimpleRegistrationEventPublisher
            ├─ MessageNotificationObserver.onRegistrationEvent(event)
            │    ├─ existsByEventKey(event.eventKey())
            │    └─ save(Message)          // 唯一约束兜底
            ├─ EmailNotificationObserver.onRegistrationEvent(event)   // CR-02
            │    ├─ shouldNotify(event)    // 仅直接通过、审核通过、审核拒绝
            │    ├─ existsByEventKey(event.eventKey())
            │    ├─ emailSender.send(EmailMessage)
            │    └─ emailLogRepository.save(EmailLog)
            └─ 观察者抛异常 → NotificationFailureLogger.log(event, error)
```

**邮件范围（CR-02）：** `SUBMITTED + APPROVED`（直接报名通过）、`APPROVED`（审核通过）、`REJECTED`（审核拒绝）；`SUBMITTED + PENDING` 与 `CANCELLED` 不写邮件。判定基于事件类型与报名状态，不额外加布尔字段。

**邮件失败：** `MockEmailSender` 先写一条 `FAILED` 记录（含错误），再抛 `EmailSendError`；`EmailNotificationObserver` 不吞掉异常，发布者捕获后写失败日志。报名/审批事务已提交，因此不回滚。

**幂等：** `eventKey = registrationId + ":" + eventType`。`existsByEventKey` 先查；并发下唯一约束冲突也视为“已通知/已发送”，不向用户报错。

**失败隔离：** 发布者对每个观察者单独 `try/except`，失败交给 `NotificationFailureLogger.log(event, error)`，继续调用下一个观察者。因此：

- 通知失败不会让 `submit/review/cancel` 抛异常；
- 报名/审批结果已提交，页面仍显示成功；
- 日志包含时间、`eventKey`、`registrationId`、观察者类名、异常摘要，便于补偿。

**已读：** `NotificationQueryService.markRead(studentId, messageId)` 先 `findById` 加载消息，校验 `message.studentId == studentId`，调用 `message.markRead()`，再 `messageRepository.update(message)`。归属不符返回 `NOT_FOUND`，不泄露消息是否存在；重复标记已读是幂等的。

**为什么不用消息队列：** 初始版本单机、事件量小、没有跨进程消费者；引入 MQ 会增加部署、序列化、重试、死信队列的成本，而当前只需要“解耦 + 失败留痕”。观察者接口保留，未来替换为 MQ 发布者时，服务层不需要改。

### 4.5 统计子系统（UC7）

`StatisticsService.forActivity(activityId)`：

1. `ActivityRepository.findById` 加载活动；不存在 → `NOT_FOUND`。
2. `RegistrationRepository.statistics(activityId)` 用一条聚合 SQL 同时取已通过数、待审核数与剩余名额：

```sql
SELECT a.activity_id, a.title AS activity_title, a.capacity,
       COALESCE(SUM(CASE WHEN r.status = 'APPROVED' THEN 1 ELSE 0 END), 0) AS approved_count,
       COALESCE(SUM(CASE WHEN r.status = 'PENDING'  THEN 1 ELSE 0 END), 0) AS pending_count,
       a.capacity - COALESCE(SUM(CASE WHEN r.status = 'APPROVED' THEN 1 ELSE 0 END), 0) AS remaining_seats
FROM activities a
LEFT JOIN registrations r ON r.activity_id = a.activity_id
WHERE a.activity_id = ?
GROUP BY a.activity_id, a.title, a.capacity;
```

3. 仓储把行映射为 `ActivityStatistics`（活动名称、容量、已通过/待审核/剩余）；服务直接返回，不再二次拼装。
4. 单条 SQL 在同一读快照内完成，避免“已通过数 + 待审核数”与列表不一致（N-4）。

**范围：** 只做单活动统计；跨活动汇总、导出 Excel 不在初始版本（B-19、第 12 部分）。

### 4.6 活动浏览子系统（UC3、UC3a）

**列表：**

1. `ActivityController.list` → `ActivityService.search(keyword)` → `ActivityRepository.searchSummaries(keyword, now)`；仓储按 `start_at ASC` 返回 `ActivitySummary`，关键词做 `LIKE` 子串匹配，转义 `%`/`_`。
2. 仓储用一条 `LEFT JOIN` + `GROUP BY` 查询同时取活动字段与已通过数，避免 N+1：

```sql
SELECT a.activity_id, a.title, a.category, a.start_at, a.location, a.capacity,
       COUNT(CASE WHEN r.status = 'APPROVED' THEN 1 END) AS approved_count,
       a.capacity - COUNT(CASE WHEN r.status = 'APPROVED' THEN 1 END) AS remaining_seats
FROM activities a
LEFT JOIN registrations r ON r.activity_id = a.activity_id
WHERE a.title LIKE ? ESCAPE '\'
GROUP BY a.activity_id, a.title, a.category, a.start_at, a.location, a.capacity
ORDER BY a.start_at ASC;
```

3. 仓储映射 `remainingSeats` 与 `displayStatus`（`now >= startAt` → `STARTED`；剩余为 0 → `FULL`；否则 `OPEN`）。
4. 控制器渲染列表；空结果给空状态，不报错。

**详情：** `ActivityController.detail` 调用 `ActivityService.findById`、`RegistrationService.findActive(studentId, activityId)`（当前学生在该活动的有效报名）、`StatisticsService.forActivity`（剩余名额），组装页面模型；不直接访问 Repository。

**为什么 `ActivitySummary` 是值对象而不是实体：** 它是“列表展示”的只读快照，包含聚合计数；把它做成实体会让 `Activity` 承担查询职责，破坏领域边界。

### 6.2 关键查询与 SQL 要点

**查有效报名：**

```sql
SELECT * FROM registrations
WHERE activity_id = ? AND student_id = ?
  AND status IN ('PENDING', 'APPROVED')
LIMIT 1;
```

**名额计数（已通过）：**

```sql
SELECT COUNT(*) FROM registrations
WHERE activity_id = ? AND status = 'APPROVED';
```

**审批列表：**

```sql
SELECT r.registration_id, r.activity_id, a.title AS activity_title,
       r.student_id, s.name AS student_name, r.status, r.created_at
FROM registrations r
JOIN students s ON s.student_id = r.student_id
JOIN activities a ON a.activity_id = r.activity_id
WHERE r.activity_id = ? AND r.status = 'PENDING'
ORDER BY r.created_at ASC;
```

**我的报名：**

```sql
SELECT r.registration_id, r.student_id, s.name AS student_name,
       r.activity_id, a.title AS activity_title, r.status, r.created_at
FROM registrations r
JOIN students s ON s.student_id = r.student_id
JOIN activities a ON a.activity_id = r.activity_id
WHERE r.student_id = ?
ORDER BY r.created_at DESC;
```

**消息列表：**

```sql
SELECT * FROM messages
WHERE student_id = ?
ORDER BY created_at DESC;
```

**邮件记录（CR-02）：**

```sql
SELECT email_id, event_key, registration_id, student_id, recipient,
       subject, content, status, error, created_at
FROM email_log
ORDER BY created_at DESC
LIMIT ?;
```

**关键词转义：** `keyword.replace('\\', '\\\\').replace('%', '\\%').replace('_', '\\_')`，SQL 使用 `LIKE ? ESCAPE '\'`，防止用户输入 `%` 变成通配符。

### 6.3 事务与并发实现

- 事务管理器提供 `with transaction(write=True):`：`write=True` 时 `BEGIN IMMEDIATE`，否则 `BEGIN`；正常退出 `COMMIT`，异常 `ROLLBACK`。它是基础设施层的上下文管理器接口（`TransactionManager`），由组合根注入 `RegistrationService`/`ActivityService`；该类画在架构类图的基础设施接口区，领域类图不重复。
- `submit/review/cancel` 使用 `write=True`；统计/列表使用只读连接。
- SQLite 连接按请求创建（或线程本地），`check_same_thread=False` 仅在明确加锁时使用；推荐每请求独立连接，避免跨线程复用。
- 写事务中不做网络/文件 IO；通知在事务外执行。
- `busy_timeout=5000`：并发写等待最多 5 秒；超时返回 `PERSISTENCE_ERROR` 并提示重试。

### 6.4 N+1 与性能

- 活动列表：1 条 `JOIN + GROUP BY` 查询，O(1) 查询数，不随活动数增长。
- 统计页：2 条查询（活动存在性 + 聚合），均为 O(1)。
- 审批页：1 条待审核列表查询；学生姓名可在列表 SQL 中 `JOIN students`，避免逐条查。
- 初始规模 200 活动、单活动几百报名，上述查询足够；不做分页/缓存（第 12 部分列为扩展）。

**结果对象约定：**

- 预期内的业务失败（重复、满员、状态冲突）用 `RegistrationResult`/`ActivityResult` 返回，不抛异常穿过层边界。
- 非预期异常（SQL 错误、配置缺失）由控制器统一捕获，返回 `PERSISTENCE_ERROR`/`POLICY_NOT_CONFIGURED`，记录堆栈到服务端日志，不暴露给用户。
- `RegistrationResult.registration` 在失败时为 `Optional.empty()`；成功时包含最新状态。

**`RegistrationContext` 的字段：** `student`（含 `studentId`、`grade`）、`activity`、`now`、`approvedCount`。策略与资格规则只读这些信息；不把 Repository 传进策略或规则，避免反向依赖持久化。

**`StudentRepository` 的边界：** 登录适配器用它加载学生身份；`RegistrationService.submit` 用它加载年级（CR-01）与邮箱（CR-02）；审批列表需要学生姓名时仍由 `RegistrationRepository` 的 JOIN 一次取回，避免 N+1。

## 第 9 部分 系统错误处理

### 9.1 错误码表

| 错误码 | HTTP | 触发条件 | 用户提示 | 处理 |
|---|---|---|---|---|
| `VALIDATION_ERROR` | 400 | 必填缺失、格式错误、容量 ≤0、开始时间不合法 | 具体字段错误 | 保留表单，不写库 |
| `UNAUTHORIZED` | 401 | 未设置演示会话 | 请先选择演示身份 | 跳转演示入口 |
| `FORBIDDEN` | 403 | 角色不匹配 | 无权执行该操作 | 记录审计日志 |
| `NOT_FOUND` | 404 | 活动/报名/消息不存在，或不属于当前学生 | 资源不存在 | 返回列表/404 页 |
| `ACTIVITY_CLOSED` | 409 | 活动已开始 | 报名已截止 | 不创建报名 |
| `DUPLICATE_ACTIVE` | 409 | 已有 `PENDING/APPROVED` 报名 | 你已报名该活动 | 不新增 |
| `GRADE_NOT_ALLOWED` | 409 | 活动配置了允许年级且学生年级不在集合内（CR-01） | 该活动仅限 X、Y 年级报名，你的年级为 Z | 不创建报名、不发通知 |
| `SEATS_FULL` | 409 | 已通过数 ≥ 容量 | 名额已满 | 不创建/不批准 |
| `ALREADY_HANDLED` | 409 | 报名不是 `PENDING` | 该申请已被处理 | 刷新列表 |
| `INVALID_STATE` | 409 | 取消时的状态迁移非法 | 当前状态不允许该操作 | 刷新 |
| `ACTIVITY_HAS_REGISTRATIONS` | 409 | 删除有报名（含历史）的活动 | 该活动已有报名记录，不能删除 | 不删除 |
| `CAPACITY_BELOW_APPROVED` | 409 | 新容量 < 已通过数 | 容量不能小于当前已通过人数 | 不保存 |
| `POLICY_IMMUTABLE` | 409 | 有有效报名时改报名方式 | 已有有效报名，不能修改报名方式 | 不保存 |
| `POLICY_NOT_CONFIGURED` | 500 | 工厂找不到策略 | 活动报名方式配置错误 | 记录日志，不建记录 |
| `PERSISTENCE_ERROR` | 500 | SQL/连接/超时 | 操作失败，请重试 | 回滚，记录堆栈 |
| `NOTIFICATION_FAILED` | 不返回 | 观察者写消息失败 | 页面仍显示成功，提示“通知稍后送达” | 写 `notification-failure.log` |
| （邮件失败不新增错误码） | 不返回 | 模拟邮件发送失败（CR-02） | 报名/审批结果照常显示成功 | `email_log=FAILED` + `notification-failure.log` |

### 9.2 故障预防与补救

1. **输入校验 + 数据库约束双保险**：应用层给友好提示，`CHECK`/唯一索引/外键防绕过。
2. **事务回滚**：任何写操作异常都回滚，不产生半条记录。
3. **并发控制**：`BEGIN IMMEDIATE` 串行化写；唯一索引兜底重复；`busy_timeout` 避免立即失败。
4. **通知失败留痕**：日志包含 `eventKey`、`registrationId`、观察者、异常；提供补偿脚本按 `eventKey` 重放。
5. **删除保护**：有报名拒绝删除；外键 `RESTRICT` 兜底。
6. **重启一致性**：无内存缓存；启动时检查表/索引；WAL checkpoint。
7. **日志与备份**：应用日志按天滚动；数据库每日备份；演示前手动备份。

### 9.3 系统维护设计

- **迁移**：`migrations/001_init.sql` 等编号脚本；启动时按版本表执行未应用脚本。
- **健康检查**：`/healthz` 返回数据库连通性与版本号；不暴露敏感配置。
- **演示数据**：`seed.py` 创建 2 个学生、1 个管理员、2 个活动（直接/审核各一），可重复执行（幂等）。
- **日志级别**：INFO 记录用例入口/结果；WARNING 记录业务拒绝；ERROR 记录持久化/通知失败；不记录密码（本设计无密码）。

### 10.4 并发测试方法

1. 两个线程各自创建连接，使用 `threading.Barrier(2)` 同时调用 `submit`/`review`。
2. 断言：成功数 = 1；失败码 ∈ {`SEATS_FULL`, `DUPLICATE_ACTIVE`}；数据库计数 ≤ 容量；有效报名 ≤ 1。
3. 重复运行 50 次，统计失败率；若出现 `SQLITE_BUSY`，检查 `busy_timeout` 与事务范围。

### 10.5 通知失败测试

1. 注入一个 `FailingObserver`（`onRegistrationEvent` 抛 `RuntimeError`），注册到发布者。
2. 调用 `submit`；断言返回成功、报名存在、`MessageNotificationObserver` 仍写入了消息（如果它排在失败观察者之后）。
3. 断言 `logs/notification-failure.log` 含 `eventKey` 与异常摘要。
4. 重启后报名仍存在（通知失败不影响持久化）。

## 第 11 部分 设计原则与模式（摘要）

完整论证见 `04-设计原则与模式.md`；这里只给结论与落点。

| 原则/模式 | 落点 | 解决的问题 | 成本 |
|---|---|---|---|
| SRP | 实体 / 服务 / 策略 / 观察者 / 仓储分层 | 一个类只承担一类变化原因 | 类数量增加，需要包结构 |
| OCP | `RegistrationPolicy`、`RegistrationObserver`、`EligibilityRule` | 新增报名方式/通知渠道/资格约束不改主流程 | 抽象与工厂/订阅/组合代码 |
| LSP | 两个策略实现同一契约；资格规则实现同一 `check` 契约 | 策略/规则可替换，不破坏服务后置条件 | 需要契约测试 |
| ISP | 小接口（策略、观察者、按聚合拆仓储） | 调用方不依赖不需要的方法 | 接口数量增加 |
| DIP | 服务依赖 Repository/Publisher/TransactionManager 接口 | 可换 SQLite、可单测 | 组合根注入 |
| GRASP 信息专家 | `Activity` 判断容量/时间；`Registration` 判断状态 | 行为放在最了解数据的对象 | 实体方法增多 |
| GRASP 创建者 | `RegistrationService` 创建 `Registration` | 创建逻辑集中，便于事务 | 服务职责略增 |
| GRASP 控制器 | 5 个控制器按用例分组 | 界面与业务解耦 | 控制器数量增加 |
| GRASP 保护变化 | 策略 + 观察者 + 仓储 | 隔离报名方式/通知渠道/存储变化 | 间接层 |
| Strategy | 报名初始状态 | 消除主流程 `if policyType` | 4 类（接口 + 2 实现 + 工厂） |
| Composite（变体） | `CompositeEligibilityRule` 组合 `GradeEligibilityRule` | 资格规则可叠加、顺序执行、返回首个违规 | 2 类 + 1 违规值对象（CR-01） |
| Observer | 报名事件 → 站内消息 + 模拟邮件 | 通知渠道与报名解耦、失败隔离、幂等 | 同步调用、幂等处理（CR-02 增加 1 实现 + 1 发送器） |
| Factory | 策略注册表 | 策略选择集中、可配置 | 注册表初始化 |
| Repository | 五个聚合接口 | 领域不依赖 SQL、可测试 | 映射代码 |
| Value Object | `RegistrationContext`、`RegistrationResult`、`ActivitySummary` | 跨层传值、减少参数 | 构造与映射 |

**不用模式的地方：**

- 不为 CRUD 引入 Command/UnitOfWork 全套框架；事务管理器只做 `BEGIN/COMMIT/ROLLBACK`。
- 不引入通用事件总线；只有一种领域事件，发布者接口足够。
- 不做泛型 Repository；五个聚合的查询差异大，泛型会迫使调用方做类型转换。

## 第 12 部分 扩展预案与变更影响分析

> 教师变更单 CR-01/CR-02 已发布并实现；本章保留初始版本的扩展预案（12.1～12.3），实际变更见第 13 部分。预分析里的“CR-2 邮件”与实际变更方向一致，但实际实现增加了邮件记录仓储与查询页面，类数比预估多。

### 12.1 可能变更与影响

| 变更 | 涉及类/接口 | 新增 | 不需要改 | 数据库 | 测试 | 预计指标 |
|---|---|---|---|---|---|---|
| CR-1 新增“抽签/候补”报名方式 | `PolicyType`、`RegistrationPolicyFactory`、`RegistrationStatus`（若加候补状态） | `LotteryRegistrationPolicy` / `WaitlistRegistrationPolicy` | `RegistrationService` 主流程、观察者、仓储接口 | `activities.policy_type` 的 CHECK 增枚举；可能加 `waitlist_position` | 策略单测 + 报名集成 + C1～C10 回归 | +1～2 类；核心服务修改 0；回归失败 0 |
| CR-2 新增邮件通知 | `RegistrationObserver` 实现、组合根 | `EmailNotificationObserver` | `RegistrationService`、`SimpleRegistrationEventPublisher`、`MessageNotificationObserver` | 无（或加 `notification_log`） | 观察者单测 + 失败隔离 + 幂等 | +1 类；核心类修改 0 |
| CR-3 活动取消/归档 | `Activity`、`ActivityService`、`ActivityRepository`、列表查询 | `ArchiveActivityService`（或方法）、`archived_at` | 报名策略、观察者 | `activities.archived_at`；查询过滤 | 归档用例 + 列表/报名边界 + 回归 | 修改 3～4 类；新增 1 类 |
| CR-4 多管理员并发/多实例 | Repository 实现、事务管理器 | PostgreSQL 实现、迁移脚本 | 领域层、策略、观察者接口 | 连接串、序列/索引 | 并发 + 事务 + 回归 | 基础设施替换；核心服务 0 修改 |
| CR-5 列表分页/多条件筛选 | `ActivityRepository.searchSummaries` 签名、`ActivitySummary` | `PageResult<ActivitySummary>` | 实体、策略、通知 | 可能加索引 | 查询 + 页面 + 回归 | 修改 2 类；新增 1 值对象 |

### 12.2 为什么这些变更“应该”小

- **策略**：服务只调用 `decideInitialStatus`；新增方式不改调用点。若新方式需要额外校验（如抽签资格），在策略外新增“资格规则”接口，而不是把公共规则塞进策略。
- **观察者**：发布者只遍历 `RegistrationObserver`；新增渠道只需实现接口并在组合根订阅。
- **Repository**：服务依赖接口；换数据库只改实现与 SQL。
- **值对象**：`RegistrationContext` 已包含策略所需的最小信息；新增策略若需要更多上下文，扩展该对象而不是让策略查库。

### 12.3 变更流程（与实验要求对齐）

1. 收到 CR 后先写影响分析：涉及类、接口、数据库、测试、风险。
2. 在 `baseline-v1` 上开分支，不删除重建。
3. 先加失败测试，再改实现；跑全部 C1～C10 + 新增用例。
4. 记录指标：新增类数、修改的核心业务类数、回归失败数、AI 交互轮次、修改总时长。
5. 在设计说明书追加“变更版”章节，保留初版图与变更版图的差异。

## 第 13 部分 变更设计：CR-01 年级限定与 CR-02 模拟邮件（change-v2）

> 本节是 v1.2 新增内容，记录教师变更单的实际设计、实现与回归结果。完整影响分析见 `../docs/CR-01-CR-02-影响分析.md`；本节只保留与设计图、代码、测试直接对应的结论。

### 13.1 变更范围与约束

| 变更 | 教师要求 | 不变的部分 |
|---|---|---|
| CR-01 年级限定 | 活动可设允许年级；仅指定年级可报名；不符时明确拒绝；原有直接/审核报名不受影响 | 名额、开始时间、重复报名、状态迁移、站内通知 |
| CR-02 模拟邮件 | 直接通过、审核通过、审核拒绝三类事件在站内消息之外写模拟邮件；失败不回滚；重复事件不重复发送；不得把邮件代码写进 `RegistrationService` | 报名/审批事务、原有站内消息、页面主流程 |

**设计约束：** 只做本地模拟邮件，不接 SMTP；数据库变更必须能迁移已有 baseline-v1 数据；`RegistrationService` 主流程只增加一个资格检查钩子，不出现邮件代码。

### 13.2 CR-01：为什么用“资格规则”而不是新策略

**问题：** 年级限制回答的是“是否允许创建报名”，而 `RegistrationPolicy` 的契约只回答“创建后初始状态是 `APPROVED` 还是 `PENDING`”。把年级塞进策略会导致：

1. 策略需要表达“拒绝且不创建记录”，污染“只决定初始状态”的契约；
2. 直接/审核两个策略都要重复年级判断；
3. 未来新增“抽签/候补”策略时还要再复制一次。

**备选：**

| 方案 | 结论 | 理由 |
|---|---|---|
| 新增 `PolicyType.GRADE_LIMITED` | 否决 | 年级不是报名方式；会与 DIRECT/APPROVAL 组合爆炸 |
| 在 `RegistrationService.submit` 写 `if activity.allowed_grades...` | 否决 | 主流程硬编码，新增资格条件继续膨胀 |
| 新增 `RegistrationPolicy.canSubmit` | 否决 | 策略职责变成“资格 + 状态”两件事，违背 SRP |
| **可组合 `EligibilityRule`** | **采用** | 与报名方式正交；顺序执行；返回首个违规；可独立单测 |

**采用结构：**

```text
RegistrationService.submit
  └─ checkEligibility(context)
       └─ CompositeEligibilityRule.check(context)
            └─ GradeEligibilityRule.check(context)
                 ├─ activity.allowed_grades is None → 通过（baseline 行为）
                 ├─ student.grade ∈ allowed_grades → 通过
                 └─ 否则 → EligibilityViolation(GRADE_NOT_ALLOWED, 允许年级 + 当前年级)
```

**规则顺序（与顺序图、活动图一致）：**

1. 活动存在且未删除；
2. 活动未开始；
3. 无重复有效报名；
4. 年级资格（CR-01）；
5. 名额未满；
6. 报名策略决定初始状态。

年级检查放在名额之前：年级不符时不应给出“名额已满”的误导性原因；且年级规则不需要计数，先做更便宜。

**类与职责：**

| 类 | 职责 | 关键方法 |
|---|---|---|
| `EligibilityRule` | 资格规则抽象 | `check(context)` |
| `CompositeEligibilityRule` | 组合多个规则，按顺序返回首个违规 | `check(context)`、`add(rule)` |
| `GradeEligibilityRule` | 年级判断与提示文本 | `check(context)` |
| `EligibilityViolation` | 错误码 + 用户可读原因 | `code`、`message` |
| `Activity` | 保存允许年级、判断年级、生成提示 | `allowedGrades`、`isGradeAllowed`、`gradeRequirementText` |
| `Student` | 年级与模拟邮箱 | `grade`、`email` |
| `RegistrationContext` | 把学生加入规则上下文 | `student` |

**兼容性：** `allowed_grades is None` 时 `GradeEligibilityRule` 直接返回 `None`，因此 baseline-v1 的活动行为完全不变；已有数据库通过 `ALTER TABLE ... ADD COLUMN` 增加字段，默认 `NULL`。

**数据：** `students.grade`（1—4，`CHECK`）、`students.email`（可空）、`activities.allowed_grades`（逗号分隔的 1—4 子集，空 = 不限）。演示学生覆盖 1—4 四个年级，便于验收。

### 13.3 CR-02：为什么用观察者而不是在服务里发邮件

**问题：** 邮件是通知渠道之一，不应让报名服务知道“邮件”存在；同时要满足失败隔离与幂等。

**备选：**

| 方案 | 结论 | 理由 |
|---|---|---|
| 在 `RegistrationService` 里直接调用邮件发送器 | 否决 | 违反依赖方向；邮件失败会污染报名事务；新增渠道继续改服务 |
| 在 `MessageNotificationObserver` 里顺带发邮件 | 否决 | 一个观察者承担两个渠道，失败隔离与幂等边界混乱 |
| **新增 `EmailNotificationObserver` 订阅同一发布者** | **采用** | 与站内消息并列；发布者逐个 `try/catch`；邮件代码不进入服务 |

**采用结构：**

```text
RegistrationService
  └─ RegistrationEventPublisher.publish(event)     // 事务提交后
       └─ SimpleRegistrationEventPublisher
            ├─ MessageNotificationObserver  → messages
            └─ EmailNotificationObserver    → email_log
                 ├─ shouldNotify(event)
                 ├─ emailLogRepository.existsByEventKey(eventKey)
                 ├─ emailSender.send(EmailMessage)
                 └─ emailLogRepository.save(EmailLog)
```

**邮件范围：**

| 事件 | 报名状态 | 站内消息 | 模拟邮件 |
|---|---|---|---|
| `SUBMITTED` | `APPROVED`（直接报名通过） | ✓ | ✓ |
| `SUBMITTED` | `PENDING`（审核型提交） | ✓ | ✗ |
| `APPROVED` | `APPROVED`（审核通过） | ✓ | ✓ |
| `REJECTED` | `REJECTED`（审核拒绝） | ✓ | ✓（含理由） |
| `CANCELLED` | `CANCELLED` | ✓ | ✗ |

**幂等：** `eventKey = registrationId + ":" + eventType`；`messages.event_key` 与 `email_log.event_key` 都是 UNIQUE。先 `existsByEventKey`，并发冲突按“已发送”处理。

**失败隔离：** `MockEmailSender` 先写 `SENT`；注入故障时改写 `FAILED` + `error`，再抛 `EmailSendError`。`EmailNotificationObserver` 不吞异常，发布者捕获后写 `logs/notification-failure.log`；因事务已提交，报名/审批结果不回滚，页面仍显示成功。

**为什么 `EmailSender` 与 `EmailLogRepository` 分开：** 发送器只负责“发”（当前是模拟写记录），仓储负责“查/存记录”；管理员查询走 `EmailLogQueryService`，与发送路径解耦，未来换真实 SMTP 时只替换 `EmailSender` 实现，查询与幂等不变。

### 13.6 设计模式复盘

1. **Strategy 没被滥用**：年级限制与初始状态是两个变化轴，强行塞进策略会让契约同时承担“准入”和“状态”两件事；资格规则是更小的抽象。
2. **Observer 得到第二次验证**：新增邮件渠道只加一个实现 + 组合根订阅，`RegistrationService`、发布者、站内消息观察者均未改调用方式。
3. **幂等放在数据层**：`event_key` 唯一约束是最终防线，应用层 `exists` 只是快速路径；重复事件在并发下也不会写出第二条。
4. **失败隔离的边界**：邮件失败写 `FAILED` 后抛出，发布者负责日志；业务事务不包含通知，因此不会被“通知失败”拖回滚。
5. **代价**：类型数增加较多（14），其中 4 个是接口/抽象；对课程规模可接受，换来的是规则、渠道、存储三处独立可测。
