## 1. 变更摘要

### CR-01 年级限定报名

- `Student` 新增 `grade`（1—4）。
- `Activity` 新增可选 `allowedGrades`；为空表示不限年级。
- 仅当学生年级属于活动允许集合时可报名；否则拒绝并给出明确原因。
- 年级规则与名额、活动开始时间、重复报名等公共约束同时生效。
- 原有直接报名、审核报名行为不变。

### CR-02 模拟邮件通知

- 在站内消息之外，对“直接报名通过、审核通过、审核拒绝”事件增加模拟邮件。
- `MockEmailSender` 记录收件人、主题、内容、状态、时间。
- 邮件失败必须记录错误，但不得回滚已提交的报名。
- 同一业务事件不得重复发送；原有站内通知继续运行。

## 3. CR-01 设计选择

### 3.1 备选方案

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| A. 新增报名策略 | 新增 `GradeLimitedPolicy`，在 `decideInitialStatus` 中处理年级 | 不改策略接口 | 策略契约被污染：策略本应只决定初始状态，却要表达“拒绝”；年级不符没有报名记录，不能返回状态；还需新增 `PolicyType`，与“报名方式”语义混淆 |
| B. 可组合资格规则 | `Activity.allowedGrades` + `EligibilityRule` 组合；`RegistrationService` 在策略之前统一检查 | 符合原设计“公共规则在服务、策略只决定初始状态”；新增规则只加类；年级规则可复用到其他活动类型 | `RegistrationService` 需要增加一个通用钩子；需要加载 `Student` |
| C. 在控制器/页面判断 | 只在界面层拦截 | 改动最小 | 规则可被绕过；服务层无权威校验；不满足“公共约束”要求 |

### 3.2 选择

**方案 B：可组合资格规则。**

理由：

1. 原设计已明确区分“公共规则”和“报名方式策略”。年级限定与名额、时间、重复报名同属“是否允许报名”的资格约束，不属于“提交后是已通过还是待审核”的初始状态决策。
2. 方案 B 不新增 `PolicyType`，不改变 `RegistrationPolicy` 契约，原有直接/审核策略零修改。
3. `CompositeEligibilityRule` 让规则可叠加（年级、院系、会员等），符合变更单“可组合规则设计”的期望。
4. 代价是 `RegistrationService.submit` 增加一次学生加载和一次规则调用；这是有边界的核心修改，换来后续资格规则的扩展点。

### 3.3 规则顺序

`活动存在 → 活动未开始 → 无重复有效报名 → 年级资格 → 名额未满 → 策略决定初始状态`。

先判年级再判名额：年级不符是“报名资格”问题，提示更准确；名额已满时也不会创建记录。所有失败路径都不写报名、不发通知。

### 3.4 数据与兼容

- `Activity.allowedGrades` 为空 → 完全保持 baseline-v1 行为。
- `Student.grade` 默认 1；演示账号显式设置 2/3/1/4，便于验收。
- 旧数据库启动时自动补列（`ALTER TABLE ... ADD COLUMN`），不清空数据。

## 4. CR-02 设计选择

### 4.1 备选方案

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| A. 在 `RegistrationService` 中直接发邮件 | 事务提交后调用 `EmailSender` | 直观 | 核心服务依赖邮件细节；新增渠道就要改核心；违反开闭原则 |
| B. 新增观察者 | `EmailNotificationObserver` 订阅 `RegistrationEvent`，与站内消息观察者并列 | 复用现有发布/失败隔离/幂等；核心服务零修改；新增渠道只加观察者 | 需要新增邮件记录仓储与发送适配器 |

### 4.2 选择

**方案 B：新增观察者。**

- `EmailNotificationObserver` 只处理 `SUBMITTED+APPROVED`、`APPROVED`、`REJECTED`；待审核提交与取消不发邮件（变更单只要求“报名通过、审核通过或拒绝”）。
- 幂等键沿用 `eventKey = registrationId:eventType`；`email_log.event_key` 唯一约束兜底。
- `MockEmailSender` 先写 `email_log`（`SENT`/`FAILED`），失败再抛 `EmailSendError`；发布者捕获后写 `logs/notification-failure.log`，不回滚报名。
- 邮件正文不重复活动标题，保留 `activityId` 供页面生成链接；与站内消息保持同一口径。

## 6. 风险与缓解

| 风险 | 影响 | 缓解 |
|---|---|---|
| 旧数据库无 `grade`/`allowed_grades` 列 | 启动失败 | 启动时 `PRAGMA table_info` 检查并 `ALTER TABLE` 补列；演示账号回填 |
| 年级规则放在策略中导致契约污染 | 策略无法表达“拒绝”，产生错误状态 | 采用资格规则，策略接口不变 |
| 邮件失败回滚报名 | 数据不一致 | 邮件在事务提交后由观察者发送；发布者捕获异常只记日志 |
| 邮件重复发送 | 学生收到多封 | `event_key` 先查后插 + 唯一约束；重复事件直接跳过 |
| 邮件失败后无法重试 | 学生漏收 | 初始版本按“同一事件最多一次尝试”处理，FAILED 记录可人工排查；重试队列列为后续演进 |
| 年级限制误伤原有活动 | 回归失败 | `allowedGrades=None` 时行为完全不变；C1—C10 全量回归 |
| 表单年级值非法 | 数据污染 | 路由解析 + `ActivityService` 双重校验；数据库 CHECK |

## 9. 决策记录

- **D-CR01-01**：不新增 `PolicyType`；年级限定是资格规则，不是报名方式。
- **D-CR01-02**：规则顺序为“存在→未开始→无重复→年级→名额→策略”。
- **D-CR02-01**：邮件只覆盖“直接报名通过、审核通过、审核拒绝”，待审核提交与取消不发邮件。
- **D-CR02-02**：邮件失败记录 `FAILED` + 发布者日志，不回滚；同一 `eventKey` 最多一次发送尝试。
- **D-CR02-03**：新增管理员邮件记录页，作为“记录收件人、主题、内容、状态、时间”的可检查证据。
