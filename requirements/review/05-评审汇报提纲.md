# 评审汇报提纲（15 分钟）

> 目标：让评审人在 15 分钟内理解“做什么、为什么这样建模、哪里最需要被挑战”。  
> 原则：先结论后证据；不逐页念文档；把时间留给关键规则、跨图一致性和已知风险。  
> 配套：`../SRS.md`、`../../uml/01-usecase.drawio`、三张顺序图、设计类图、`../../uml/04-设计原则与模式.md`。

---

## 1. 时间分配

| 时间 | 内容 | 目的 |
|---|---|---|
| 0～1 min | 背景与目标 | 为什么做 CampusEvent |
| 1～3 min | 范围、角色、用例总览 | 边界是否合理 |
| 3～6 min | 关键业务规则 | 名额/重复/审批/通知/取消/删除 |
| 6～8 min | 需求→设计→测试追踪 | 是否闭合、可验收 |

| 14～15 min | 请评审人重点看什么 | 引导问题 |

## 2. 逐页提纲

### 第 1 页：封面

- 项目：CampusEvent 校园活动报名与管理系统。
- 评审对象：初始 SRS v1.0-rc1 + 用例模型 + UML/设计基线。
- 评审目标：编码前确认需求完整、设计可落地、测试可验收。
- 一句话结论：**范围小、规则集中、关键交互已画清；请重点挑战名额/审批/通知/取消边界。**

### 第 2 页：问题与目标

- 现状痛点：人工/表格报名容易重复、超卖、状态不透明。
- 目标：一个统一的活动发布、报名、审批、通知、统计系统。
- 不做什么：登录、邮件/短信、候补/抽签、跨活动报表、软删除、移动端。
- 成功度量：C1～C10 全过；并发不超卖；通知失败可追踪；评审 S1/S2 关闭。

### 第 3 页：角色与用例总览

- 两个业务参与者：学生、管理员；固定演示账号，不做登录。
- 8 个主用例 + 1 个扩展：UC1 创建、UC2 编辑/删除、UC3 浏览、UC3a 详情、UC4 报名、UC5 取消、UC6 审批、UC7 统计、UC8 通知。
- **UC3a 用 `«extend»`**：列表本身完整，详情是条件增强。
- **UC4 不拆直接/审核两个用例**：触发器/目标相同，只是初始状态不同。

### 第 4 页：关键业务规则（评审重点）

- 名额只算“已通过”；待审核不占；剩余 = max(0, 容量 - 已通过)。
- 同一学生同一活动最多一条待审核/已通过；历史保留、可再申请。
- 直接报名→已通过；审核型→待审核；批准时**再次**检查名额。
- 通知失败**不回滚**报名/审批；同一报名同一事件只一条消息。
- 取消：本人、待审核/已通过可取消；已通过释放名额；开始后仍可取消（A-05）。
- 删除：有报名（含历史）拒绝删除；不做软删除。
- 统计：单活动、三数一致、不出现负剩余。

### 第 5 页：需求→设计→测试追踪

- P2-F01～F08 → FR-01～FR-08 → UC1～UC8 → 设计元素 → C1～C10/E1～E10。
- 例：P2-F05 审批 → FR-05 → UC6 → `RegistrationService.review` + `Registration` → C6～C8/E3/E10。
- RTM 在 SRS §6.2；没有“只画图不写理由”的条目。
- 验收不是只有正常路径：E1～E10 覆盖开始后报名、并发、通知失败、删除、改方式、降容量、越权、再次申请、重复审批。

### 第 6 页：用例图与分析类图

- 用例图：只有参与者、用例、关联、一条 `«extend»`；不画实现类。
- 分析类图：ECB，只回答“需要哪些职责”，不出现 Controller/Service/Repository/DAO。
- 分析到设计的拆/合/新增在 `设计说明书.md` 2.3.1 有理由（如活动管理/浏览页面合并为 `ActivityController`）。

### 第 7 页：设计类图与策略

- 领域实体：Student、Activity、Registration、Message。
- `RegistrationPolicy` 接口 + Direct/Approval 两个实现 + Factory。
- **策略只决定初始状态**；活动状态/重复/名额是公共规则，留在报名协调处与实体。
- 成本：多 4 个类与一次工厂查找；收益：新增抽签/候补不改主流程。
- 反例：把名额检查放进策略会导致两套规则、策略依赖仓储、审批复查管不到。

### 第 8 页：顺序图（报名/审批/取消）

- 报名：活动存在/开始 → 重复 → 名额 → 策略分支 → 保存 → 提交后发布事件 → 通知（失败只记日志）。
- 审批：先校验待审核 → 批准复查名额 → 通过/拒绝 → 更新 → 通知；名额不足保持待审核。
- 取消：归属/状态校验 → 取消 → 更新 → 通知；已通过释放名额。
- 片段嵌套完整；生命线都能在类图中找到；消息与方法对应（`failure/success` 是页面结果消息）。

### 第 9 页：状态图与活动图

- 四状态：PENDING/APPROVED/REJECTED/CANCELLED；拒绝/取消终态。
- 迁移守卫：approve/reject 仅 PENDING；cancel 仅 PENDING/APPROVED；非法迁移拒绝。
- 活动图：公共规则判定顺序（活动可报名→无重复→名额）→ DIRECT/APPROVAL 分流 → 保存/事件/通知汇合；失败路径不创建报名。

### 第 10 页：设计原则与取舍

- SOLID：实体/服务/策略/观察者/仓储职责分离；服务依赖接口；策略可替换；接口小而专。
- GRASP：信息专家（容量/时间在 Activity，状态在 Registration）；创建者；控制器；保护变化。
- Observer：报名先落库，事件提交后发布；每个观察者独立 try/catch；失败写日志；去重键避免重复。
- 事务：`BEGIN IMMEDIATE` 串行化写 + 唯一性兜底；批准复查名额是最终防线。
- 明确不做：通用事件总线、CQRS、事件溯源、泛型 Repository、软删除、乐观锁（当前规模）。

### 第 11 页：已知风险与待确认

- 见 `06-待确认问题清单.md`，重点：开始后取消、满员是否允许待审核、删除/软删除、通知正文是否带活动名、拒绝理由是否必填、多管理员并发编辑。
- 已知取舍：单机 SQLite 写吞吐有限；通知是进程内同步，崩溃窗口存在；用日志+补偿脚本兜底，不宣称最终一致。
- 不隐藏：通知失败、容量并发、删除策略都有明确边界与测试。

### 第 12 页：请评审人重点看什么

1. SRS 的 FR/BR 是否与用例规格、状态图、顺序图有矛盾。
2. 名额/重复/审批复查/通知失败/取消/删除六类规则是否有漏。
3. 三张顺序图的生命线/消息是否与设计类图一致。
4. 策略是否只决定初始状态；公共规则是否只有一套。
5. C1～C10/E1～E10 是否足以验收；RTM 是否闭合。
6. 哪些假设需要教师确认（见 Q-01～Q-12）。

## 3. 常见问题与回答要点

| 评审人可能问 | 回答要点 |
|---|---|
| 为什么直接/审核不拆两个用例？ | 触发器/目标相同，只是结果状态不同；拆开会把报名方式固化进需求模型，新增方式还要加用例。 |
| 为什么名额检查不放进策略？ | 名额与报名方式无关；放策略会两套实现、策略依赖仓储、审批复查管不到。策略只决定初始状态。 |
| 通知失败会不会丢报名？ | 不会。报名先落库，提交后发布事件；观察者失败只写日志，不回滚；页面仍显示业务成功。 |
| 怎么避免重复通知？ | 同一报名同一事件一个去重键；先查后写，唯一约束兜底；重复事件忽略。 |
| 并发批准最后一个名额怎么办？ | 写事务串行化 + 批准时重新计数；只有一个成功，另一个名额不足、保持待审核。 |
| 为什么有报名就不能删活动？ | 历史与统计完整性；软删除会让所有查询都要过滤，初始版本选择拒绝并提示。 |
| 开始后为什么还能取消？ | 需求只限制“开始后不得新增报名”；A-05 明确允许取消；若教师要求禁止，加一条公共规则即可。 |
| 通知正文为什么没有活动名？ | 事件只带最小事实；通知页用活动关联显示名称，避免活动改名后历史消息不一致。 |
| 为什么没有登录？ | 实验二初始版本用固定演示账号；角色/归属校验仍在，不能越权。 |
| 单机 SQLite 能撑住吗？ | 课程规模 200 活动/500 报名/10 并发；写事务串行化；不宣称高并发，变更版再评估。 |

## 4. 5 分钟短版（时间被压缩时）

1. 一句话：8 个用例、2 种报名方式、4 个状态、3 张关键顺序图；编码前请评审需求与设计。
2. 三条硬规则：名额只算已通过；批准复查名额；通知失败不回滚。
3. 两个设计决策：策略只决定初始状态；观察者解耦通知并做失败隔离/去重。
4. 一张追踪：P2-F0x → FR → UC → 设计元素 → C/E。
5. 三个待确认：开始后取消、满员是否允许待审核、删除/软删除。
6. 请评审人：先看顺序图与状态图是否和 SRS 矛盾，再看 RTM 是否闭合。

## 5. 汇报纪律

- 不念文档；每页只讲结论 + 证据。
- 不辩护；评审人提问先确认“是事实问题还是取舍问题”。
- 不隐藏风险；已知问题放第 11 页，主动请评审人判断。
- 不超时；15 分钟到点停止，剩余问题转书面/复审。
- 记录员同步记问题，作者不现场改文档。
