# 需求评审检查表（R1）

> 评审对象：`../SRS.md`、`../../uml/02-usecase-specs.md`、`../../uml/01-usecase.drawio`  
> 使用方式：预读时逐条标记；会议中只讨论“问题/不适用”的条目；不要把“通过”当默认值。  
> 结果填写：`通过` / `问题` / `N/A`；有问题时在“问题ID/证据”列写 `R1-REQ-xxx` + 位置。

| ID | 检查项 | 通过标准 | 结果 | 问题ID/证据 |
|---|---|---|---|---|
| **A. 范围、角色与假设** | | | | |
| A-01 | 范围边界 | SRS 明确“做什么/不做什么”；P2-F01～F08 全部在范围内；范围外清单与实验二一致。 |  |  |
| A-02 | 角色与权限 | 学生/管理员目标、权限、数据可见性清楚；不存在第三方参与者被误画/漏画。 |  |  |
| A-03 | 假设与依赖 | A-01～A-12 有影响与验证方式；假设不掩盖必须确认的需求。 |  |  |
| A-04 | 优先级 | 8 条功能需求有高/中优先级；与用例规格、C1～C10 的重要性一致。 |  |  |
| A-05 | 成功度量 | 有可判定的完成条件（C1～C10、并发、通知失败、评审签名）。 |  |  |
| **B. 功能需求** | | | | |
| B-01 | P2 覆盖 | P2-F01～F08 均能追到至少一条 FR、一个 UC、一个 C/E 验收。 |  |  |
| B-02 | 需求陈述完整 | 每条 FR 有角色、触发/前置、基本流、异常/替代、后置条件。 |  |  |
| B-03 | 活动管理 | 创建/编辑/删除的字段、校验、删除条件、失败提示完整。 |  |  |
| B-04 | 浏览/详情 | 列表筛选、剩余名额、展示状态、详情按钮状态、无活动/无匹配/活动被删处理完整。 |  |  |
| B-05 | 报名 | 活动开始前限制、重复有效报名、名额检查、初始状态、失败不产生记录均有描述。 |  |  |
| B-06 | 取消 | 归属/状态校验、二次确认、名额释放、通知、失败回滚语义完整。 |  |  |
| B-07 | 审批 | 待审核列表、批准复查名额、拒绝理由、状态冲突、并发批准处理完整。 |  |  |
| B-08 | 通知 | 生成时机、去重、失败留痕、不改变业务结果、查看/已读边界完整。 |  |  |
| B-09 | 统计 | 已通过/待审核/剩余口径一致；单活动范围；查询失败降级。 |  |  |
| B-10 | 用例建模 | UC3a 用 `«extend»`；直接/审核型不拆成两个用例；不为内部校验建 `«include»`。 |  |  |
| **C. 业务规则** | | | | |
| C-01 | 名额口径 | 只有“已通过”占名额；待审核不占；剩余 = max(0, 容量 - 已通过)。 |  |  |
| C-02 | 重复报名 | 同一学生同一活动最多一条待审核/已通过；历史记录不限制。 |  |  |
| C-03 | 再次申请 | 已拒绝/已取消可再次申请；生成新记录，旧记录保留。 |  |  |
| C-04 | 报名方式变更 | 有有效报名时禁止改报名方式；仅有历史时允许。 |  |  |
| C-05 | 容量调整 | 容量不得小于已通过数；下调后不影响已通过记录。 |  |  |
| C-06 | 状态迁移 | 四种状态与合法迁移完整；终态不再迁出；非法迁移有拒绝语义。 |  |  |
| C-07 | 审批边界 | 只有待审核可审批；批准复查名额；名额不足保持待审核。 |  |  |
| C-08 | 通知规则 | 失败不回滚；同一报名同一事件只一条消息；拒绝理由可选写入内容。 |  |  |
| C-09 | 取消时间 | 取消是否受活动开始限制有明确假设（A-05）；与 BR-16 一致。 |  |  |
| C-10 | 删除策略 | 有报名（含历史）拒绝删除；无报名才可删；与 BR-13 一致。 |  |  |
| **D. 非功能需求** | | | | |
| D-01 | 性能 | 有数据规模、P95/响应时间口径；不是“快速/流畅”。 |  |  |
| D-02 | 并发一致性 | 有并发场景、重复次数、0 超卖/0 重复有效报名的判定。 |  |  |
| D-03 | 持久化/可靠 | 重启一致、无半条记录、通知失败不回滚有验收。 |  |  |
| D-04 | 安全/权限 | 角色/归属/跨学生访问/未授权操作有可测试的预期。 |  |  |
| D-05 | 易用/兼容/可维护 | 中文、错误提示、浏览器矩阵、回归/自动化有度量或检查方式。 |  |  |
| **E. 数据与接口** | | | | |
| E-01 | 数据实体 | Student/Activity/Registration/Message 的字段、类型、约束、关系完整。 |  |  |
| E-02 | 数据一致性 | 唯一性、外键/引用、状态枚举、时间字段与业务规则一致。 |  |  |
| E-03 | 保留与隐私 | 历史保留、学生只看自己、管理员只看审批字段、无敏感信息过度收集。 |  |  |
| E-04 | 外部接口 | 明确“无外部系统”；站内通知不被误写成第三方接口；Web 界面有约束。 |  |  |
| E-05 | 时间口径 | 本地时间/ISO-8601/不处理时区有一致说明。 |  |  |
| **F. 验收与追踪** | | | | |
| F-01 | C1～C10 | 每条有 Given/When/Then；覆盖直接/审核/重复/满员/审批/拒绝/取消/重启。 |  |  |
| F-02 | E1～E10 | 覆盖开始后报名、并发、通知失败、删除、改方式、降容量、越权、再次申请、重复审批。 |  |  |
| F-03 | RTM | P2-F0x → FR → UC → 设计元素 → C/E 闭合；状态列不虚假声称“已测试”。 |  |  |
| F-04 | NFR 验证 | 每条 NFR 有验证方法/证据，不只是“应满足”。 |  |  |
| F-05 | 变更控制 | 评审后变更走影响分析与基线更新；不直接改代码绕过需求。 |  |  |
| **G. 表达质量** | | | | |
| G-01 | 无方案混入 | 正文不出现类/框架/数据库/模式等实现词；设计追踪只在附录。 |  |  |
| G-02 | 无模糊词 | 没有“快速/友好/稳定/尽量/等”未度量表述。 |  |  |
| G-03 | 编号与命名 | FR/NFR/BR/DR/C/E/A/Q 编号唯一；术语与用例规格一致。 |  |  |
| G-04 | 引用有效 | 文件/章节/图名引用存在；表格列数一致；无 TODO/占位。 |  |  |
| G-05 | 无矛盾 | SRS 与用例规格、状态图、活动图、顺序图在规则/状态/边界上无矛盾。 |  |  |
