# CampusEvent 需求与设计评审包（v1.0-rc1）

> 目的：让同组/他组同学在**编码前**评审需求与设计，发现问题、签字放行。  
> 评审对象：初始 SRS、用例规格、UML 图、设计说明书、设计原则报告。  
> 评审结论：通过 / 有条件通过 / 返工；至少 2 名同学签名后才能进入 AI 实现。

## 4. 怎么提问题

问题编号规则：

```text
R1-REQ-001   需求评审第 1 号问题
R1-UML-001   需求评审中发现的 UML/一致性问题
R2-DES-001   设计评审第 1 号问题
R2-CON-001   设计评审中的跨图一致性问题
```

每条问题至少写清：

1. **位置**：文件 + 章节/图名 + 元素（如 `SRS.md §4.3 BR-06`、`07-审批报名-sequence.drawio` 的 `alt` 片段）。
2. **类型**：缺失 / 矛盾 / 歧义 / 不可验证 / 不可追踪 / 设计缺陷 / 一致性问题 / 建议。
3. **严重度**：S1 阻断、S2 严重、S3 一般、S4 建议（定义见 `01-评审指南.md`）。
4. **证据**：引用原文/图元/消息，避免“感觉不对”。
5. **建议**：可操作的修改方向；不要求评审人重写文档。
6. **负责人/状态**：作者认领，记录“待处理/已修改/待复审/关闭”。

**纪律：** 评审会只记录问题，不现场改文档；作者只答疑，不辩护；有争议的条目由主持人标记“需复审”。

## 5. 评审重点（最容易出问题的地方）

1. **范围**：P2-F01～F08 是否都有需求、用例、验收；范围外是否被偷偷加进来。
2. **规则**：名额只算已通过；重复有效报名；批准复查名额；通知失败不回滚；取消是否受开始时间限制。
3. **一致性**：SRS 的 FR 与 UC1～UC8 是否同名同义；类名/方法名/状态枚举是否与三张顺序图、状态图一致。
4. **可验证**：每条 FR 是否有 C/E 验收；NFR 是否有度量；有没有“快速/友好/尽量”。
5. **设计合理性**：策略是否只决定初始状态；公共规则是否在报名协调处；观察者是否真正解耦；事务边界是否说清。
6. **可追踪**：P2-F0x → FR → UC → 设计元素 → C/E 是否闭合。

## 6. 评审出口与签名

| 结论 | 条件 | 后续 |
|---|---|---|
| 通过 | 无 S1/S2；S3/S4 有处理计划 | 更新基线；编码准入“通过”；至少 2 人签名 |
| 有条件通过 | 无 S1；S2 有负责人/日期 | 3 个工作日内复审；关闭 S2 后放行 |
| 返工 | 有 S1，或 S2 > 3 条 | 修改后重新评审；不得进入编码 |

签名表在 `04-评审记录与签到表.md`。未签名前，`设计说明书.md` 附录 E 的“编码准入”保持“未通过”。

---

## 7. 评审后作者要做什么

1. 24 小时内把问题录入 `04-评审记录与签到表.md`，标严重度与负责人。
2. S1 立即修；S2 在复审前修；S3/S4 排入下一版或说明不修理由。
3. 修改后更新：
   - `../SRS.md` 的版本/变更记录/RTM；
   - `02-usecase-specs.md` 的用例/规则；
   - 对应 `.drawio` 图与 `设计说明书.md`；
   - `04-设计原则与模式.md`（如果取舍变化）。
4. 复审只检查问题关闭与受影响条目，不重复全文走查。
5. 关闭后把评审结论、签名、日期回填 SRS 第 7 节与设计说明书附录 E。
