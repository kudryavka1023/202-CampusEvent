## 1. 引言

### 1.1 目的

本文档把实验二 CampusEvent 的初始需求整理为可评审、可验收、可追踪的软件需求规格，供三类读者使用：

1. **评审人**：判断需求是否完整、一致、无歧义、可验证，是否与用例图和用例规格一致。
2. **实现者**：在编码前明确“做什么、做到什么程度、什么算完成”，不自行补需求。
3. **测试者**：把每条需求映射到验收用例 C1～C10 和边界用例 E1～E10，设计测试而不只测正常路径。

本文档**不**规定采用什么技术、如何存储数据或如何拆分模块；这些属于设计说明书与设计原则报告的评审范围。

### 1.2 范围

**初始版本范围（P2-F01～P2-F08）：**

- 管理员创建、编辑、删除活动，设置名称、类型、开始时间、地点、人数上限、报名方式。
- 学生浏览活动列表、按名称筛选、查看活动详情。
- 学生提交报名、取消自己的报名；同一活动禁止重复有效报名。
- 两种报名方式：直接报名（提交即通过）与审核型报名（提交后待审核）。
- 管理员查看待审核报名，批准或拒绝；批准时再次检查名额。
- 报名状态：待审核、已通过、已拒绝、已取消；状态迁移符合规则。
- 报名/审批/取消结果写入站内消息；学生查看并标记已读。
- 管理员按活动查看已通过数、待审核数、剩余名额。

**范围外（初始版本不做）：**

- 注册、登录、找回密码、复杂 RBAC；使用固定演示账号。
- 邮件、短信、微信推送；只做站内消息。
- 活动图片、富文本、评论、签到、问卷。
- 候补队列、抽签、随机分配。
- 跨活动汇总报表、导出 Excel。
- 活动取消/归档、软删除。
- 移动端 App、第三方日历同步。
- 消息队列、缓存、微服务拆分。

### 1.3 术语与缩写

| 术语 | 定义 |
|---|---|

## 2. 总体描述

### 2.1 产品视角

CampusEvent 是一个面向校园的**独立 Web 系统**，不替代学校教务系统，也不与外部系统做实时集成。学生通过浏览器查看活动并报名；管理员通过管理端发布活动、审批报名、查看统计。系统内部保存活动、报名、站内消息三类业务数据与学生身份数据，服务重启后数据仍然一致。

系统边界：

```text
学生 ──浏览/报名/取消/通知──> CampusEvent ──活动/报名/统计/消息──> 管理员
                                      │
                                      └── 本地持久化数据（活动、报名、消息、学生）
```

不画外部系统，因为初始版本没有外部系统接口；站内通知是系统内部职责，不是外部参与者。

### 2.2 主要功能

|---|---|---|---|---|

| FR-02 | 活动查看 | 学生浏览/筛选活动列表，查看活动详情与剩余名额。 | P2-F02 | 高 |

| FR-04 | 报名方式 | 直接报名自动通过；审核型报名进入待审核。 | P2-F04 | 高 |
| FR-05 | 审批 | 管理员查看待审核列表，批准或拒绝；批准时复查名额。 | P2-F05 | 高 |

### 2.3 用户/角色

| 角色 | 目标 | 典型场景 | 权限 |
|---|---|---|---|
| 学生（Student） | 找到感兴趣的活动并完成报名，随时了解结果。 | 浏览列表 → 查看详情 → 报名/取消 → 查看通知。 | 浏览活动、查看详情、提交/取消自己的报名、查看自己的通知。 |
| 管理员（Admin） | 发布活动、控制名额、审批报名、掌握报名情况。 | 创建活动 → 查看待审核 → 批准/拒绝 → 查看统计。 | 创建/编辑/删除活动、查看待审核列表、批准/拒绝、查看统计。 |
| 演示入口（非业务角色） | 在无登录模块时切换演示身份。 | 选择学生/管理员演示账号。 | 仅演示环境启用，不参与业务用例。 |

**权限边界：**

- 学生只能查看/操作自己的报名与通知；不能查看其他学生的报名或通知。
- 管理员只能看到审批所需的字段（学生姓名、提交时间、状态），不提供“查看某学生全部报名/通知”的入口。
- 角色不匹配的操作应被拒绝，且不泄露资源是否存在。

### 2.5 成功度量

初始版本达到以下条件才算“需求完成”：

1. C1～C10 全部通过；E1～E10 无阻断/严重缺陷。
2. 并发报名/审批不突破容量，不产生重复有效报名。
3. 通知失败不回滚报名/审批结果，且失败可追踪。
4. 评审无未关闭的 S1/S2 问题；至少 2 名同学签名通过。
5. 需求、设计、测试之间可通过 RTM 追溯。

## 3. 需求分析

### 3.1 需求来源与层次

| 层次 | 本项目的回答 | 主要来源 |
|---|---|---|
| 业务需求 | 校园活动报名仍靠人工/表格，容易出现重复、超卖、状态不透明；需要一个统一的活动发布与报名系统。 | 实验二背景、P2-F01～F08 |
| 用户需求 | 学生要“找活动、报名、取消、看结果”；管理员要“发活动、控名额、审批、看统计”。 | 用例图、UC1～UC8 |
| 系统功能需求 | 系统应提供活动管理、浏览、报名/取消、审批、状态、通知、统计八类服务。 | 第 4.1 节 |
| 非功能需求 | 性能、并发一致性、持久化、权限、易用性、可维护性、兼容性、可追踪。 | 第 4.2 节 |
| 业务规则/数据 | 名额、重复、状态迁移、删除、通知、数据字段与约束。 | 第 4.3/4.4 节 |

### 3.2 业务流程

**活动生命周期：**

1. 管理员创建活动，填写名称、类型、开始时间、地点、容量、报名方式。
2. 活动出现在学生端列表；学生可查看详情。
3. 学生在活动开始前报名；系统按公共规则与报名方式决定初始状态。
4. 审核型报名由管理员批准/拒绝；批准时复查名额。
5. 学生可取消自己的待审核/已通过报名。
6. 活动开始后不再接受新报名；历史报名保留。
7. 有报名记录的活动不能删除；避免历史丢失与孤立记录。

**报名判定顺序（从外到内）：**

1. 活动存在且未删除？
2. 当前时间早于活动开始时间？
3. 该学生在该活动是否已有待审核/已通过的有效报名？
4. 已通过数是否小于容量？
5. 按报名方式决定初始状态：直接报名 → 已通过；审核型 → 待审核。
6. 保存报名；提交成功后生成站内通知；通知失败只留痕，不撤销报名。

**审批判定顺序：**

1. 报名存在且状态为待审核？
2. 批准时：活动存在；已通过数是否小于容量？
3. 名额充足 → 已通过；名额不足 → 保持待审核，批准失败。
4. 拒绝 → 已拒绝；拒绝理由可选，写入通知内容。
5. 保存结果；提交成功后生成站内通知；通知失败只留痕。

**取消判定顺序：**

1. 报名存在且属于当前学生？
2. 状态为待审核或已通过？
3. 改为已取消；若原为已通过，释放名额。
4. 保存结果；提交成功后生成站内通知；通知失败只留痕。

> 活动图与顺序图见 `../uml/10-activity-报名流程.drawio`、`../uml/07-提交报名-sequence.drawio`、`../uml/07-审批报名-sequence.drawio`、`../uml/07-取消报名-sequence.drawio`。本文只保留需求级判定顺序，不展开对象协作。

| 用例 | 名称 | 主要参与者 | 对应需求 | 优先级 |

| UC1 | 创建活动 | 管理员 | P2-F01 | 高 |
| UC2 | 编辑/删除活动 | 管理员 | P2-F01 | 高 |
| UC3 | 浏览/筛选活动 | 学生 | P2-F02 | 高 |
| UC3a | 查看活动详情 | 学生 | P2-F02 | 高 |
| UC4 | 提交报名 | 学生 | P2-F03、F04、F06、F07 | 高 |
| UC5 | 取消报名 | 学生 | P2-F03、F06、F07 | 高 |

**建模结论：**

1. **UC3a 用 `«extend»` 扩展 UC3，不用 `«include»`。** 基用例“浏览/筛选活动”只显示列表时仍然完整；查看详情只在学生选择某一活动时发生，可能 0 次。
2. **直接报名与审核型报名不拆成两个用例。** 两者触发器相同（点击报名）、目标相同（完成一次报名申请），只是初始状态不同；拆开会把“报名方式”变化点固化在需求模型里。
3. **不为“校验名额/校验重复/写通知”建 `«include»`。** 它们是 UC4/UC5/UC6 的内部规则或后置职责，不是参与者可独立启动、有独立可观测结果的用例。
4. **每个用例都有规格说明。** 详细基本流/扩展流见 `../uml/02-usecase-specs.md` 第 6 节；本文只做需求级归纳。

### 3.4 领域概念

| 概念 | 职责/含义 | 关键关系 |
|---|---|---|
| 学生（Student） | 报名与通知的接收者；只能操作自己的数据。 | 1 个学生有 0..* 条报名；1 个学生有 0..* 条消息。 |
| 活动（Activity） | 可报名的校园活动；定义容量、开始时间、报名方式。 | 1 个活动有 0..* 条报名；1 个活动关联 0..* 条消息。 |
| 报名（Registration） | 学生与活动之间的一次申请，带状态与时间戳。 | 属于 1 个学生、1 个活动；状态四值。 |
| 站内消息（Message） | 报名/审批/取消结果的通知，带已读标记。 | 属于 1 个学生、关联 1 个活动。 |

**状态：**

- 待审核（PENDING）：已提交，等待管理员处理；不占名额。
- 已通过（APPROVED）：报名成功；占 1 个名额。
- 已拒绝（REJECTED）：管理员拒绝；不占名额；终态。
- 已取消（CANCELLED）：学生取消；不占名额；终态。

**关系示意：**

```text
学生 1 ──< 报名 >── 1 活动
学生 1 ──< 消息 >── 1 活动
```

> 领域概念用于界定需求词汇与数据约束，不是设计类图；设计类图另见 `../uml/06-design-class.drawio`。

### 3.5 公共规则与报名方式差异

| 规则 | 是否随报名方式变化 | 需求侧处理 |
|---|---|---|
| 活动存在、未删除、未开始 | 否 | 所有报名统一检查；开始后拒绝新增报名。 |
| 无重复有效报名 | 否 | 同一学生同一活动最多一条待审核/已通过；历史记录不限制。 |
| 名额未满 | 否 | 只统计已通过；待审核不占名额；两种方式提交时都检查。 |
| 角色/归属正确 | 否 | 学生只能操作自己的报名/通知；管理员才能审批。 |
| 初始状态 | **是** | 直接报名 → 已通过；审核型 → 待审核。 |
| 是否需要审批 | **是**（由初始状态隐含） | 只有待审核需要审批；不额外增加“是否需要审批”布尔字段。 |

**结论：** 公共规则集中在报名业务协调处统一检查，报名方式只决定“初始状态”。这样新增抽签/候补时不需要复制名额、重复、活动状态规则；但初始版本不实现抽签/候补。

### 3.6 范围边界

**做：** 活动管理、浏览/详情、报名/取消、审批、状态、站内通知、单活动统计。

**不做：** 见 1.2 节“范围外”。范围外内容不得在实现中“顺手加”，除非走变更单并做影响分析。

### 3.7 需求分析结论

1. **范围可控**：8 个功能域、2 个业务角色、4 个核心数据实体；初始版本不引入登录、外部通知、候补/抽签、跨活动报表。
2. **用例模型稳定**：UC1～UC8 覆盖 P2-F01～F08；UC3a 用 `«extend»`；直接/审核型作为 UC4 的两条结果路径，不拆用例。
3. **规则边界清楚**：名额、重复、活动状态、角色/归属是公共规则；报名方式只决定初始状态。这样后续加抽签/候补时不需要复制公共规则。
4. **主要风险集中在四处**：并发名额竞争、审批复查、通知失败、删除/取消边界；C4/C8/E2/E3/E4/E5/E8 已专门覆盖。
5. **需要评审人重点确认**：Q-01～Q-12 的假设与取舍，尤其是开始后取消、满员是否允许待审核、删除/软删除、通知正文是否带活动名。

#### 4.1.2 关键功能需求说明

**FR-01 活动管理**

- 需求陈述：管理员应能创建、编辑、删除活动；活动字段完整、容量为正整数、创建/编辑时开始时间晚于当前时间；有报名记录的活动不得删除。
- 触发/前置：管理员进入管理端；目标活动存在（编辑/删除时）。
- 基本流：打开表单 → 填写/修改 → 校验 → 保存 → 返回列表并提示成功。
- 异常/替代：必填缺失/格式错误、容量 ≤0、开始时间不晚于当前、报名方式非法、活动不存在、容量小于已通过数、有有效报名时改报名方式、删除时有报名、保存失败。
- 后置条件：成功时活动字段持久化；删除成功时无孤立报名；删除被拒绝时数据不变。
- 验收：C1、E5、E6、E7。

**FR-02 活动查看**

- 需求陈述：学生应能浏览活动列表、按名称子串筛选、查看活动详情与自己的报名状态。
- 触发/前置：学生进入学生端；详情要求活动存在且未删除。
- 基本流：打开列表 → 系统加载活动与剩余名额 → 显示卡片 → 输入关键词筛选 → 选择活动进入详情。
- 异常/替代：无活动、筛选无匹配、活动被删除、统计查询失败（剩余名额显示“—”）。
- 后置条件：只读，不改变业务数据。
- 验收：C1、C2。

**FR-03 报名/取消**

- 需求陈述：学生应能在活动开始前提交报名；同一活动不得重复有效报名；学生应能取消自己的待审核/已通过报名。
- 触发/前置：学生进入学生端；报名要求活动存在且未开始；取消要求报名属于当前学生且状态为待审核/已通过。
- 基本流（报名）：点击报名 → 加载活动 → 检查活动状态/重复/名额 → 按报名方式确定初始状态 → 保存 → 通知 → 显示结果。
- 基本流（取消）：打开我的报名 → 选择记录 → 二次确认 → 校验归属/状态 → 改为已取消 → 保存 → 通知 → 刷新列表与名额。
- 异常/替代：活动不存在/已开始、重复有效报名、名额已满、报名方式非法、并发重复/名额竞争、通知失败、保存失败；取消时报名不存在/非本人/状态不允许/通知失败/保存失败。
- 后置条件：成功时恰有一条新报名或一条状态变更；失败时原数据不变。
- 验收：C2～C5、C9、E1、E2、E8、E9。

**FR-04 报名方式**

- 需求陈述：直接报名在公共规则通过后立即变为已通过；审核型报名进入待审核，等待管理员处理。
- 触发/前置：同 FR-03；报名方式由活动配置决定。
- 基本流：公共规则检查 → 直接报名创建已通过记录 / 审核型创建待审核记录 → 保存 → 通知。
- 异常/替代：报名方式非法/未配置时拒绝报名并记录；不得把公共规则复制到某一种方式里。
- 后置条件：直接报名占用 1 个名额；审核型不占名额。
- 验收：C2、C5。

**FR-05 审批**

- 需求陈述：管理员应能查看某活动的待审核报名，批准或拒绝；批准时再次检查名额。
- 触发/前置：管理员进入管理端；报名存在且状态为待审核。
- 基本流：打开审批页 → 列出待审核 → 选择记录 → 再次加载/校验状态 → 批准（复查名额）或拒绝（可选理由）→ 保存 → 通知 → 刷新列表与统计。
- 异常/替代：报名不存在、状态不是待审核、批准时名额已满、并发批准最后一个名额、通知失败、保存失败。
- 后置条件：批准成功→已通过并占名额；拒绝成功→已拒绝；失败时状态不变。
- 验收：C6、C7、C8、E3、E10。

**FR-06 状态管理**

- 需求陈述：系统应只允许四种状态及合法迁移：待审核→已通过/已拒绝/已取消；已通过→已取消；已拒绝/已取消为终态。
- 触发/前置：报名/审批/取消操作。
- 基本流：校验当前状态 → 执行迁移 → 保存 → 通知。
- 异常/替代：非法迁移（如已拒绝再批准、已取消再取消）应拒绝并提示“该报名已处理/当前状态不允许”。
- 后置条件：状态与保存后的数据、统计、页面显示一致。
- 验收：C2、C5～C9。

**FR-07 站内通知**

- 需求陈述：报名/审批/取消成功后，系统应生成站内消息；同一报名同一事件只生成一条；通知失败不影响业务结果，但必须可追踪。
- 触发/前置：报名/审批/取消提交成功。
- 基本流：业务结果保存 → 生成通知事件 → 写站内消息 → 学生查看/标记已读。
- 异常/替代：通知写入失败→记录失败日志（报名 ID、事件类型、错误），业务结果保留；重复事件→按去重键忽略。
- 后置条件：学生能看到结果；通知失败时页面仍显示业务成功，并提示“通知稍后送达”。
- 验收：C2、C6、C7、C9、E4。

**FR-08 统计**

- 需求陈述：管理员应能按活动查看已通过数、待审核数、剩余名额；剩余名额只由已通过数计算。
- 触发/前置：管理员进入统计页；活动存在。
- 基本流：选择活动 → 统计已通过/待审核 → 计算剩余 → 显示。
- 异常/替代：活动不存在→提示；统计查询失败→提示“统计暂时不可用”，不影响业务数据。
- 后置条件：只读；不改变数据。
- 验收：C8、C9。

| DR-03 | 报名（Registration） | 报名 ID、活动 ID、学生 ID、状态、创建/更新时间 | 状态四值；同一学生同一活动最多一条待审核/已通过；历史不限。 | 历史保留；学生看自己；管理员审批看必要字段。 |
| DR-04 | 站内消息（Message） | 消息 ID、学生 ID、活动 ID、内容、创建时间、已读标记、去重键 | 去重键在同一报名同一事件上唯一；已读默认否。 | 历史保留；学生只看自己；管理员不查看。 |
| DR-05 | 枚举 | 报名状态、报名方式、事件类型 | 状态：PENDING/APPROVED/REJECTED/CANCELLED；方式：DIRECT/APPROVAL；事件：SUBMITTED/APPROVED/REJECTED/CANCELLED。 | 与页面显示、统计、状态图一致。 |

**数据保留与隐私：**

- 初始版本不删除报名历史与消息；活动只有无任何报名时才能删除。
- 学生姓名/学号只用于身份与审批展示；不收集密码、联系方式、身份证号等敏感信息。
- 学生不能查看其他学生的报名或通知；管理员只能看到审批所需字段。

### 4.5 外部接口

| 编号 | 接口 | 对方系统/角色 | 数据/协议 | 频率 | 失败处理 |
|---|---|---|---|---|---|
| EI-01 | 学生/管理员 Web 界面 | 浏览器用户 | HTML 表单/页面，中文；POST 操作有防伪造请求保护 | 按用户操作 | 提示错误、保留输入、不写半条数据。 |
| EI-02 | 外部系统接口 | 无 | 初始版本不接邮件/短信/支付/日历/统一认证 | — | — |
| EI-03 | 站内通知 | 系统内部 | 站内消息，学生在通知页查看 | 报名/审批/取消后 | 失败留痕，不回滚业务结果。 |

> 站内通知不是外部参与者；EI-03 只用于说明“通知”这一需求边界，避免误以为要接第三方推送。

### 4.6 设计约束

| 编号 | 约束 | 理由/影响 |
|---|---|---|
| DC-01 | 单实例 Web 应用，部署到云服务器。 | 课程规模与运维成本；不引入分布式部署。 |
| DC-02 | 活动、报名、消息、学生数据持久化；重启后一致。 | C10；不允许只存内存。 |
| DC-03 | 固定演示账号；不做注册/登录/复杂权限。 | A-01；角色校验简化，但不能取消归属校验。 |
| DC-04 | 只做站内通知；不接邮件/短信/微信。 | BR-22；通知失败只留痕。 |
| DC-05 | 不做候补/抽签、跨活动报表、活动归档/软删除、移动端。 | 初始版本范围；变更单再评估。 |
| DC-06 | 时间用服务器本地时间，ISO-8601；不处理时区。 | A-10；避免跨时区复杂度。 |
| DC-07 | 数据规模约 200 活动、单活动 500 报名、10 并发用户。 | 性能与容量验收口径。 |
| DC-08 | 界面中文；错误提示不暴露堆栈或内部路径。 | NFR-05；用户可用性。 |

## 5. 验收标准

### 5.1 主要验收用例 C1～C10

| 编号 | Given（前置） | When（操作） | Then（预期） |
|---|---|---|---|
| C1 | 管理员已进入管理端；活动列表为空。 | 创建“篮球赛”，容量 2，直接报名。 | 创建成功；学生端列表可见；报名数为 0。 |
| C2 | C1 活动存在；学生 A 已进入学生端。 | A 提交报名。 | 状态“已通过”；已通过数 1；A 收到报名成功通知。 |
| C3 | A 已有一条 C2 的已通过报名。 | A 再次提交同一活动报名。 | 拒绝重复有效报名；报名记录仍为 1 条；不生成重复有效报名。 |
| C4 | C1 活动容量 2；学生 B 已报名并通过。 | 学生 C 提交报名。 | C 因名额不足失败；已通过数仍为 2；不超容量。 |
| C5 | 创建审核型活动“讲座”，容量 10；学生 A。 | A 提交报名。 | 状态“待审核”；已通过数 0；A 收到“等待审核”通知。 |
| C6 | C5 的 A 报名为待审核。 | 管理员批准 A。 | 状态“已通过”；已通过数 1；A 收到通过通知。 |
| C7 | C5 活动另一学生 B 为待审核。 | 管理员拒绝 B，理由“名额调整”。 | 状态“已拒绝”；B 收到含理由的通知；不占名额。 |
| C8 | 审核型活动容量 1；A 已通过；B 待审核。 | 管理员批准 B。 | 批准失败（名额已满）；B 仍待审核；已通过数 1；不超容量。 |
| C9 | A 有一条待审核或已通过报名。 | A 取消报名。 | 状态“已取消”；若原为已通过，剩余名额 +1；统计同步；A 收到取消通知。 |
| C10 | 已完成 C1～C9。 | 重启服务后查询活动、报名、通知。 | 数据与重启前一致；无孤立报名；历史记录保留。 |

### 5.2 边界与并发用例 E1～E10

| 编号 | 场景 | 预期 |
|---|---|---|
| E1 | 活动已开始后提交报名。 | 拒绝，提示“报名已截止”；不创建报名。 |
| E2 | 两名学生并发抢最后一个名额。 | 恰好 1 人成功；已通过数 ≤ 容量；另一人名额不足。 |
| E3 | 两名管理员并发批准最后一个名额。 | 恰好 1 人成功；另一人批准失败；已通过数 ≤ 容量。 |
| E4 | 通知写入抛异常。 | 报名/审批/取消结果仍成功；失败可追踪；页面不因通知失败显示业务失败。 |
| E5 | 删除有报名记录的活动（含历史）。 | 拒绝删除；活动与报名保持不变。 |
| E6 | 有有效报名时修改报名方式。 | 拒绝修改；提示“已有有效报名，不能修改报名方式”。 |
| E7 | 容量下调到小于已通过数。 | 拒绝保存；提示“容量不能小于当前已通过人数”。 |
| E8 | 学生取消他人报名。 | 拒绝；不泄露报名是否存在；原报名不变。 |
| E9 | 已拒绝/已取消后再次申请。 | 允许；生成新记录；旧记录保留；有效报名仍最多 1 条。 |
| E10 | 审批已处理报名。 | 拒绝重复审批；状态不变；提示“该申请已被处理”。 |

**验收规则：**

1. C1～C10 全部通过；E1～E10 无阻断/严重缺陷。
2. 并发用例重复 50 次，0 次超卖、0 条重复有效报名。
3. 通知失败用例中，业务结果保留且失败记录可追踪。
4. 评审无未关闭的 S1/S2 问题。
